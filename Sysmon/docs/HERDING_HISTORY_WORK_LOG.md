# 쥐몰이 알고리즘 기록 화면 작업 일지

이 문서는 System Monitor에서 쥐몰이 알고리즘의 실행 기록을 확인할 수 있도록
기능을 만드는 과정을 순서대로 정리한다. 처음 코드를 보는 팀원도 현재 무엇이
완료되었고 다음에 무엇을 해야 하는지 알 수 있게 작성한다.

## 1. 이 기능을 만드는 이유

쥐몰이 시험이 끝난 뒤 성공 또는 실패 결과만 보면 알고리즘이 왜 그런 결과를
냈는지 알기 어렵다. 원인을 확인하려면 같은 시간대의 다음 정보가 필요하다.

- 쥐가 이동한 위치
- Driver 로봇이 실제로 이동한 위치
- Blocker 로봇이 실제로 이동한 위치
- 알고리즘이 각 로봇에 계산해 준 목표 위치
- `SEARCH`, `TRACK`, `HERD`, `CAPTURED` 같은 알고리즘 상태
- 포획 성공 여부와 포획까지 걸린 시간

이 정보를 지도와 시간 순서로 다시 보여주는 것이 이번 작업의 목표다.

## 2. 데이터 저장 방식 결정

알고리즘의 원본 실행 기록은 ROS 토픽을 그대로 저장하는 `rosbag2`를 우선
사용한다. System Monitor 화면에서 재생하기 쉽게 필요한 값만 뽑은 JSON 파일도
함께 사용할 예정이다.

```text
main의 ROS 토픽
    ↓ rosbag2로 원본 기록
rosbag 디렉터리
    ↓ 변환 스크립트
Replay JSON
    ↓ System Monitor가 읽음
쥐몰이 기록 화면에서 지도·상태 재생
```

DB는 처음부터 반드시 필요한 것은 아니다. 시험 기록이 많아져 날짜, 성공 여부,
알고리즘 버전으로 검색해야 할 때 시험 요약만 SQLite에 저장하는 방식이 적합하다.
10Hz 위치 데이터나 이미지처럼 큰 원본 데이터는 rosbag 또는 JSON 파일로
보관한다.

## 3. 전체 구현 순서

- [x] 1단계: 기존 `기록 조회` 화면에 기록 종류를 선택하는 하위 탭 추가
- [x] 2단계: Replay JSON을 읽어 쥐·Driver·Blocker 경로를 지도에 표시
- [x] 3단계: 재생, 일시정지, 배속, 시간 이동 기능 추가
- [x] 4단계: 여러 시험 기록 중 하나를 선택하는 기능 추가
- [x] 5단계: rosbag을 Replay JSON으로 바꾸는 변환 기능 추가
- [ ] 6단계: 기록이 많아지면 DB에 시험 요약과 파일 경로 저장

각 단계가 끝날 때 이 문서에 완료 내용, 변경 파일, 테스트 결과를 이어서
기록한다.

## 4. 1단계 작업 기록 — 기록 종류 하위 탭

작업일: 2026-08-10

상태: 완료

### 4.1 변경 전

기존 `기록 조회` 화면에는 탐지 기록, 증거 사진, 로봇 이동 경로만 있었다.
쥐몰이 알고리즘 기록을 추가하면 서로 성격이 다른 정보가 한 화면에 섞일 수
있었다.

### 4.2 변경 후

`기록 조회` 안에 다음 두 개의 하위 탭을 추가했다.

1. `탐지·이동 기록`
   - 기존 탐지 목록, 사진, 이동 경로를 확인한다.
   - 기존 `HistoryStore` API를 그대로 사용한다.
2. `쥐몰이 기록`
   - 앞으로 알고리즘 상태와 경로 재생 화면이 들어갈 자리다.
   - 현재는 다음 단계에서 연결할 정보와 안내 문구를 보여준다.

```text
기록 조회
├── 탐지·이동 기록  ← 기존 기능
└── 쥐몰이 기록     ← 새로 추가한 영역
```

### 4.3 화면 전환 원리

각 하위 탭 버튼에는 `data-history-view`라는 값이 있다.

```html
<button data-history-view="activity">탐지·이동 기록</button>
<button data-history-view="herding">쥐몰이 기록</button>
```

사용자가 버튼을 누르면 JavaScript의 `switchHistorySubview()` 함수가 실행된다.
선택한 화면에서는 `hidden` 클래스를 제거하고, 선택하지 않은 화면에는
`hidden` 클래스를 붙인다. `hidden` 클래스가 붙은 요소는 CSS에 의해 보이지
않는다.

탐지 기록 API는 `탐지·이동 기록` 화면을 선택했을 때만 호출한다. 쥐몰이 탭을
보는 동안 불필요하게 기존 기록을 다시 요청하지 않도록 하기 위해서다.

### 4.4 변경한 파일

#### `frontend/templates/dashboard.html`

- 하위 탭 버튼 두 개를 추가했다.
- 기존 기록 화면을 `history-view-activity` 영역으로 묶었다.
- 쥐몰이 기록용 `history-view-herding` 영역을 추가했다.
- 스크린 리더도 탭 관계를 이해할 수 있도록 `role`, `aria-selected`,

#### `frontend/static/js/dashboard.js`

- 현재 선택한 기록 화면을 `activeHistorySubview`에 기억한다.
- `switchHistorySubview()`에서 버튼과 화면의 선택 상태를 변경한다.
- 기존 `loadHistory()`는 탐지·이동 기록 화면에서만 실행하도록 했다.

#### `frontend/static/css/dashboard.css`

- 선택된 탭과 선택되지 않은 탭을 색으로 구분했다.
- 쥐몰이 기록의 준비 중 화면 스타일을 추가했다.
- 작은 모바일 화면에서는 탭 너비와 안내 항목 배치를 자동으로 조정한다.

#### `backend/tests/test_app.py`

- 서버가 반환한 HTML에 두 하위 탭과 두 화면 영역이 실제로 존재하는지
  검사하는 테스트를 추가했다.

## 5. 2단계 작업 기록 — Replay JSON 전체 경로 표시

작업일: 2026-08-10

상태: 완료

### 5.1 사용한 기록 파일

저장소에 이미 있는 아래 파일을 첫 번째 예제 데이터로 사용했다.

```text
backend/system_monitor/replay_data/real_map_frames.json
```

이 JSON에는 여러 번의 시험 결과가 들어 있다. 현재 화면은 설정에서 선택된 시험
한 건을 표시한다. 한 프레임에는 대략 다음 정보가 있다.

```json
{
  "t": 32.4,
  "state": "HERD",
  "target": [1.2, -3.4],
  "driver": [0.8, -2.9],
  "blocker": [1.9, -3.1],
  "driver_goal": [1.0, -3.2],
  "blocker_goal": [2.1, -3.5],
  "capture_progress": 0.72
}
```

각 값의 의미는 다음과 같다.

- `t`: 시험 시작 후 지난 시간(초)
- `state`: 그 시점의 알고리즘 상태
- `target`: 쥐 위치
- `driver`: Driver 로봇 위치
- `blocker`: Blocker 로봇 위치
- `driver_goal`: 알고리즘이 Driver에 계산한 목표 위치
- `blocker_goal`: 알고리즘이 Blocker에 계산한 목표 위치
- `capture_progress`: 포획 진행 정도

### 5.2 데이터가 화면까지 오는 순서

```text
real_map_frames.json
    ↓ ReplayManager가 파일을 읽음
GET /api/history/herding
    ↓ 브라우저 JavaScript가 JSON 응답을 받음
요약 카드와 Canvas 지도에 결과 표시
```

`ReplayManager.history_record()`는 선택된 시험의 복사본을 반환한다. 복사본을
사용하는 이유는 화면 조회 중에 값이 바뀌더라도 프로그램이 재생에 사용하는
원본 데이터까지 실수로 변경되지 않게 하기 위해서다.

API 응답에는 다음 정보가 포함된다.

- `trial`: 성공 여부, 수행 시간, 모델명, 시간별 위치 프레임
- `driver_id`, `blocker_id`: 두 로봇의 이름
- `traps`: 포획 지점 이름과 좌표
- `map_image`: JSON 안에 저장된 배경 지도 이미지
- `photo_frame`: 지도 이미지가 나타내는 실제 좌표 범위
- `parameters`: 포획 반경, 패닉 거리, 센서 범위

### 5.3 화면에 표시되는 내용

쥐몰이 기록 탭 상단에 다음 여섯 가지 요약 값을 표시한다.

- 시험 성공 또는 실패
- 전체 수행 시간
- 사용한 알고리즘 모델
- 저장된 프레임 개수
- Driver 로봇 이름
- Blocker 로봇 이름

지도에는 선 종류를 나눠서 표시한다.

- 빨간 실선: 쥐가 실제로 이동한 경로
- 파란 실선: Driver가 실제로 이동한 경로
- 주황 실선: Blocker가 실제로 이동한 경로
- 파란 점선: 알고리즘이 Driver에게 계산한 목표 위치의 변화
- 주황 점선: 알고리즘이 Blocker에게 계산한 목표 위치의 변화
- 초록 사각형: 포획 지점

각 실제 경로의 시작점은 속이 빈 원, 마지막 위치는 색이 채워진 원과 `종료`
라벨로 표시한다. 따라서 자동 재생이 없어도 전체 이동 방향과 최종 위치를 한
화면에서 확인할 수 있다.

### 5.4 지도 좌표를 맞추는 방법

로봇과 쥐의 위치는 미터 단위의 `map` 좌표이고, 브라우저 지도는 픽셀 단위다.
따라서 JavaScript가 `photo_frame`의 최솟값과 최댓값을 이용해 미터 좌표를
Canvas 픽셀 좌표로 변환한다.

현재 Replay 지도 이미지는 90도 회전된 형태다. 코드가 이미지 비율과 좌표 범위
비율을 비교해 회전 여부를 판단한 뒤 x축과 y축의 방향을 맞춘다. 내장 지도
이미지가 없는 JSON이라면 모든 경로와 포획 지점의 최솟값·최댓값을 구해 경로가
화면 안에 들어오도록 대신 그린다.

### 5.5 데이터가 없거나 일부만 실패할 때

- 로봇이 2대보다 적거나 JSON을 읽지 못하면 서버를 종료하지 않고
  `표시할 쥐몰이 기록이 없습니다`라는 안내를 보여준다.
- 배경 지도 이미지만 깨졌다면 좌표 데이터로 경로를 계속 그린다.
- 화면 크기가 바뀌면 Canvas 크기와 경로를 다시 계산해 선이 흐려지거나
  어긋나는 것을 막는다.

## 6. 3단계 작업 기록 — 시간 순서대로 재생

작업일: 2026-08-10

상태: 완료

### 6.1 추가한 조작 기능

2단계에서 한 번에 표시하던 전체 경로를 시간 순서대로 다시 볼 수 있도록 다음
기능을 추가했다.

- 재생과 일시정지
- 처음부터 다시 보기
- 0.5배, 1배, 2배 재생 속도
- 슬라이더를 움직여 원하는 시각으로 이동
- 현재 시각의 FSM 상태와 포획 진행률 표시

쥐몰이 기록 탭을 처음 열면 마지막 프레임이 선택되어 2단계에서 만든 전체 경로가
그대로 보인다. 이 상태에서 `재생` 버튼을 누르면 자동으로 첫 프레임으로 이동한
후 시작한다.

### 6.2 화면에서 확인할 수 있는 현재 정보

재생 제어 영역에는 다음 네 가지 값이 실시간으로 바뀐다.

- `재생 시간`: 현재 시간과 전체 수행 시간. 예: `21.0 / 48.4초`
- `알고리즘 상태`: 초보자용 한글 이름과 JSON 원본 상태. 예: `쥐 몰이 (HERD)`
- `포획 진행률`: 0%부터 100%까지의 숫자와 진행 막대
- `현재 프레임`: 현재 번호와 전체 개수. 예: `211 / 484`

FSM 상태는 다음과 같이 표시한다.

- `SEARCH`: 공동 탐색
- `TRACK`: 쥐 추적
- `HERD`: 쥐 몰이
- `CORNER`: 구석 유도
- `LOST`: 대상 유실
- `CAPTURED`: 포획 완료

상태마다 색을 다르게 표시해 상태 변화도 쉽게 구분할 수 있게 했다.

### 6.3 재생이 동작하는 원리

Replay JSON의 각 프레임에는 시험 시작 후 경과 시간인 `t`가 들어 있다. 예를
들면 첫 프레임은 `0.0`, 다음 프레임은 `0.1`처럼 기록된다.

```text
브라우저에서 실제로 지난 시간
    × 선택한 배속(0.5, 1, 2)
누적 재생 시간
    ↓ 다음 프레임의 t와 비교
현재 프레임과 누적 경로 갱신
```

프레임 번호를 무조건 하나씩 더하지 않고 각 프레임의 `t`를 확인한다. 따라서
나중에 기록 간격이 0.1초가 아닌 JSON을 사용하더라도 실제 기록 시간에 맞춰
재생할 수 있다.

브라우저의 `requestAnimationFrame()`은 화면을 그리기 좋은 시점마다 재생
함수를 호출한다. 재생 중에는 현재 프레임까지의 배열만 잘라 지도에 전달하므로
쥐와 두 로봇의 경로가 이동한 만큼씩 늘어난다. 재생이 마지막 프레임에 도달하면
자동으로 멈춘다.

### 6.4 각 버튼의 동작

- `재생`: 현재 위치부터 재생한다. 마지막 프레임에서 누르면 처음부터 시작한다.
- `일시정지`: 현재 프레임과 경로를 그대로 유지한 채 시간 증가를 멈춘다.
- `처음부터`: 재생을 멈추고 첫 프레임으로 이동한다.
- `0.5배`, `1배`, `2배`: 기록 시간이 흐르는 속도를 변경한다.
- 시간 슬라이더: 재생을 멈추고 선택한 프레임으로 즉시 이동한다.

쥐몰이 기록 탭을 떠나거나 실시간 관제 화면으로 이동하면 보이지 않는 곳에서
재생이 계속되지 않도록 자동으로 일시정지한다.

### 6.5 지도 표시 변화

슬라이더나 재생으로 현재 프레임이 바뀔 때마다 다음 요소를 다시 그린다.

- 현재 시점까지의 쥐 실제 경로
- 현재 시점까지의 Driver·Blocker 실제 경로
- 현재 시점까지 계산된 Driver·Blocker 목표 경로
- 각 대상의 시작 위치와 현재 위치
- 고정된 포획 지점

중간 프레임의 마지막 점에는 `현재`, 전체 기록의 마지막 점에는 `종료`라고
표시한다. 지도 투영 범위는 항상 전체 시험 데이터를 기준으로 유지하므로 재생
도중 배경 지도의 크기나 경로 위치가 흔들리지 않는다.

## 7. 4단계 작업 기록 — 여러 시험 기록 선택

작업일: 2026-08-10

상태: 완료

### 7.1 변경 전과 변경 후

`real_map_frames.json`에는 시험이 4개 있지만 기존 화면은 실행 설정에서 정한
시험 한 건만 볼 수 있었다. 이제 쥐몰이 기록 화면의 `시험 선택` 목록에서 네
시험을 자유롭게 바꿔 확인할 수 있다.

각 선택 항목에는 다음 정보가 표시된다.

- 시험 번호
- 알고리즘 모델
- 성공 또는 실패
- 전체 수행 시간
- 포획 지점

예를 들어 두 번째 시험은 다음과 같이 보인다.

```text
시험 2 · noisy_human · 성공 · 9.9초 · 상단(top)
```

선택 영역 아래에는 현재 시험 번호, 성공 여부, 포획 지점과 랜덤 시드도 표시해
같은 조건의 알고리즘 시험을 구분하기 쉽게 했다.

### 7.2 백엔드에서 시험을 선택하는 방법

기존 API 주소에 `trial_index`라는 조회 조건을 추가했다.

```text
GET /api/history/herding                 → 실행 설정의 기본 시험
GET /api/history/herding?trial_index=0   → 첫 번째 시험
GET /api/history/herding?trial_index=1   → 두 번째 시험
```

프로그래밍에서는 번호를 0부터 세기 때문에 화면의 `시험 1`은 API에서
`trial_index=0`이다. API 응답에는 전체 시험 목록을 만드는 데 필요한
`trial_options`, 현재 선택 번호인 `selected_trial_index`, 전체 개수인
`trial_count`가 함께 들어간다.

각 `trial_options` 항목은 전체 좌표 프레임을 중복 전송하지 않고 다음 요약값만
제공한다.

- `index`, `model`, `success`
- `duration`, `frame_count`
- `goal_name`, `seed`

사용자가 존재하지 않는 시험 번호나 문자를 보내면 서버가 종료되지 않고 HTTP
400 오류와 이해할 수 있는 오류 문구를 반환한다.

### 7.3 실제 Replay 실행과 기록 선택을 분리한 이유

System Monitor가 Replay 모드로 실행 중일 때 `ReplayManager`는 설정에서 선택된
한 시험을 실시간 화면에 반복 재생한다. 기록 화면에서 다른 시험을 선택했다고
이 실행 대상까지 갑자기 바뀌면 실시간 화면을 보고 있는 다른 팀원에게 혼란을
줄 수 있다.

따라서 기록 API는 요청한 시험의 복사본만 반환한다. 기록 화면에서 시험 2를
선택해도 `ReplayManager._trial`이 가리키는 실제 실행 시험은 그대로 유지된다.
이 방식은 원본 JSON도 수정하지 않는다.

### 7.4 시험을 바꿀 때 화면에서 일어나는 일

```text
사용자가 시험 선택
    ↓ 실행 중인 기록 재생 일시정지
선택 번호로 /api/history/herding 요청
    ↓ 새 시험 데이터 수신
요약 카드·슬라이더·상태·지도 갱신
    ↓
새 시험의 마지막 프레임과 전체 경로 표시
```

시험을 바꾸면 이전 시험의 시간이 이어지지 않도록 재생 시계와 프레임을 새
시험에 맞게 초기화한다. 처음에는 마지막 프레임을 선택하므로 전체 결과를 먼저
볼 수 있고, `재생`을 누르면 해당 시험의 첫 프레임부터 시작한다.

사용자가 선택을 빠르게 여러 번 바꾸면 이전 API 응답이 늦게 도착해 최신 선택을
덮어쓸 수 있다. 이를 막기 위해 요청마다 번호를 붙이고 가장 최근 요청의 응답만
화면에 반영한다.

## 8. 5단계 작업 기록 — rosbag을 Replay JSON으로 변환

작업일: 2026-08-10

상태: 완료

자세한 현장 실행 명령과 오류 해결 방법은
[ROSBAG_TO_REPLAY_GUIDE.md](ROSBAG_TO_REPLAY_GUIDE.md)에 따로 정리했다.

### 8.1 만든 기능

Sysmon PC에서 기록한 rosbag2 디렉터리를 읽어 `쥐몰이 기록` 화면에서 바로 열 수
있는 Replay JSON 파일을 생성하는 명령어를 추가했다.

```text
rosbag2 디렉터리(metadata.yaml + *.db3 또는 *.mcap)
    ↓ convert_rosbag_to_replay.py
시간이 서로 다른 ROS 메시지를 공통 이벤트로 변환
    ↓ 0.1초 간격으로 마지막 값을 모음
Replay JSON의 frames 배열 생성
    ↓
System Monitor 쥐몰이 기록 화면에서 선택·재생
```

기본 변환 명령은 다음과 같다.

```bash
cd Sysmon/backend
python3 convert_rosbag_to_replay.py \
  ~/under_guard_bags/trial_001 \
  data/trial_001_replay.json \
  --model field_algorithm_v1 \
  --goal-name bottom
```

### 8.2 기본으로 읽는 main 토픽

- `/fleet/event`: `rat_detected:x:y` 형식의 쥐 map 좌표
- `/robot4/odom`: Driver 실제 위치
- `/robot6/odom`: Blocker 실제 위치
- `/robot4/target_pose`: Driver 계산 목표
- `/robot6/target_pose`: Blocker 계산 목표
- `/fleet/status`: Driver 상태

실제 토픽 이름이 다르면 `--driver-odom`, `--blocker-odom`, `--target-pose` 같은
명령행 옵션으로 바꿀 수 있다.

현재 main의 `detector_node.py`와 `rat_herding_node.py`에는 쥐 좌표 계산과 몰이
알고리즘이 아직 TODO로 남아 있다. 변환기만 실행한다고 없는 위치 데이터가 생기는
것은 아니다. 실제 시험 전에 `/fleet/event`에 `rat_detected:x:y`가 발행되고 두
odom 토픽이 들어오는지 확인해야 한다.

### 8.3 정밀 기록용 선택 토픽

변환기는 다음 전용 토픽도 선택적으로 읽는다.

- `/herding/state`: `SEARCH`, `TRACK`, `HERD`, `CORNER`, `LOST`, `CAPTURED`
- `/herding/capture_progress`: 0.0부터 1.0까지의 포획 진행률
- `/herding/success`: 포획 성공 여부

현재 main에는 이 토픽 발행이 아직 없다. 전용 토픽이 없으면 `/fleet/status`를
FSM 상태로 바꾸고 진행률은 기본값 0%를 쓴다. 목표 토픽이 없으면 각 로봇의 실제
위치를 목표 대체값으로 쓴 뒤 변환 완료 메시지에 주의 문구를 출력한다. 화면을
깨뜨리지는 않지만 정밀한 알고리즘 분석에는 전용 토픽 추가가 필요하다.

### 8.4 시간이 다른 토픽을 한 프레임으로 합치는 방법

odom, 쥐 탐지, 목표와 상태 메시지는 정확히 같은 시각에 도착하지 않는다. 변환기는
rosbag에 기록된 나노초 timestamp를 초 단위로 바꾸고, 기본 0.1초 간격마다 그
시점까지 받은 최신 값을 모아 한 프레임을 만든다.

```text
10.00초: Driver 위치 수신
10.03초: Blocker 위치 수신
10.05초: 쥐 위치 수신
10.10초: FSM 상태 수신
        ↓
target + driver + blocker가 모두 준비된 시각부터 프레임 생성
```

프레임을 시작하려면 쥐·Driver·Blocker 좌표가 모두 필요하다. 하나라도 시험 내내
없으면 잘못된 경로를 추측하지 않고 누락된 필드 이름을 오류로 알려준다.

각 출력 프레임에는 다음 값이 들어간다.

- 경과 시간 `t`
- 쥐·Driver·Blocker 위치
- Driver·Blocker 목표 위치
- FSM 상태와 탐지 여부
- Driver와 쥐 사이 거리
- 포획 진행률

시험 전체에는 모델명, 성공 여부, 포획 지점, 시작 위치, 발견 시각, 수행 시간과
프레임 배열이 들어간다.

### 8.5 기존 지도와 여러 시험 이어 붙이기

`--base-replay` 옵션을 사용하면 기존 JSON의 배경 지도, 좌표 범위, 포획 지점과
알고리즘 파라미터를 새 파일에 복사할 수 있다.

`--append-existing-trials`를 함께 사용하면 기존 시험 배열 뒤에 새 시험을
추가한다. 출력 파일은 임시 파일에 완성한 다음 교체하므로 쓰기 도중 문제가 생겨
기존 JSON이 절반만 저장될 가능성을 줄였다. 기존 출력 덮어쓰기는 사용자가
`--force`를 명시해야만 가능하며 원본 rosbag은 수정하지 않는다.

## 10. 평가 피드백 반영 — 전술 리플레이 가독성 개선

작업일: 2026-08-10

상태: 완료

이 작업은 DB를 만드는 6단계가 아니다. 1~5단계에서 만든 파일 기반 다시보기
화면을 실제 쥐몰이 과정을 이해하기 쉬운 형태로 다듬은 추가 개선 작업이다.

### 10.1 현재 시점과 미래 경로 구분

기존에는 재생 중인 시점보다 뒤의 경로를 구분하기 어려워 전체 결과를 미리 보는
것처럼 느껴질 수 있었다. 이제 경로를 다음 두 부분으로 나눠 그린다.

- 현재 시점까지 실제로 이동한 경로: 각 대상의 원래 색으로 진하게 표시
- 아직 지나지 않은 미래 경로: 아주 흐린 점선으로 표시

`미래 경로` 체크를 끄면 앞으로 이동할 구간을 완전히 숨길 수 있다. 재생 시간이
증가하면 진한 과거 경로가 길어지고 로봇과 쥐의 현재 위치가 함께 움직이므로,
최종 경로 그림이 아니라 시간축 기반 전술 리플레이로 볼 수 있다.

### 10.2 대상별 현재 위치 아이콘

경로가 겹쳐도 색상에만 의존하지 않도록 모양을 다르게 표시한다.

- Driver: 진행 방향을 가리키는 파란 삼각형
- Blocker: 방패 모양의 주황 오각형
- Rat: 귀가 있는 빨간 원형
- 포획 지점: 초록색 조준점 모양

Driver 삼각형은 현재 위치와 직전 위치의 차이를 이용해 진행 방향으로 회전한다.
색을 구별하기 어려운 사용자도 모양과 라벨을 함께 보고 대상을 구분할 수 있다.

### 10.3 알고리즘 상태와 거리 설명

원본 상태 코드 옆에 초보자가 이해할 수 있는 짧은 행동 설명을 추가했다. 예를
들어 `HERD` 상태에서는 Driver가 쥐를 밀고 Blocker가 이탈 방향을 막는 단계라고
안내한다.

기존의 `포획 진행률`은 `알고리즘 포획 진행률`로 이름을 구체화했다. 이 값은
화면이 임의로 계산한 재생 진행률이 아니라 Replay JSON 각 프레임의
`capture_progress` 값이다. 계산 기준은 알고리즘에서 정해야 하므로 도움말에도
그 사실을 표시한다.

진행률과 별개로 현재 쥐 위치와 선택된 포획 지점 사이의 직선거리도 표시한다.
두 좌표가 `(x1, y1)`, `(x2, y2)`라면 다음 피타고라스 공식으로 계산한다.

```text
거리 = sqrt((x2 - x1)^2 + (y2 - y1)^2)
```

예를 들어 화면에 `쥐 → 하단(bottom) 거리 0.19m`처럼 표시되므로 100%라는 숫자만
볼 때보다 포획 지점에 얼마나 가까워졌는지 구체적으로 확인할 수 있다.

### 10.4 클릭할 수 있는 주요 이벤트 타임라인

시간 슬라이더 위에 다음 주요 이벤트를 표시한다.

```text
시작 → 쥐 탐지·역할 배정 → 추적 시작 → 몰이 시작
     → 포획 지점 접근 → 대상 유실(발생한 경우) → 포획 완료
```

이벤트 버튼을 누르면 해당 상태가 처음 나타난 프레임으로 즉시 이동한다. 이미
지난 이벤트, 현재 선택된 이벤트, 아직 지나지 않은 이벤트는 서로 다른 색으로
표시한다. 시험을 바꾸면 새 시험의 프레임을 읽어 타임라인도 다시 만든다.

현재 Replay JSON에는 `ROLE_ASSIGNED`라는 별도 상태가 없다. 따라서
`discovered=true`가 처음 나타난 프레임을 `쥐 탐지·역할 배정` 이벤트로 표시한다.
향후 main에서 역할 배정 전용 상태를 기록하면 그 값을 별도 이벤트로 분리할 수
있다. 현재 데이터에 없는 시각을 임의로 만들어 넣지는 않았다.

### 10.5 경로 표시 토글

지도 위의 범례를 체크박스로 바꿔 필요한 정보만 선택할 수 있게 했다.

- 기본 표시: 쥐 실제 경로, Driver 실제 경로, Blocker 실제 경로, 포획 지점,
  미래 경로
- 기본 숨김: Driver 계산 목표, Blocker 계산 목표

평소에는 실제 이동을 중심으로 간단하게 보고, 분석할 때만 계산 목표를 켜서
알고리즘의 계획과 실제 주행 결과를 비교할 수 있다. 체크 상태를 바꾸면 API를
다시 호출하지 않고 현재 브라우저에 있는 동일한 프레임을 즉시 다시 그린다.

### 10.6 상단 정보 구조 압축

크기가 같던 여섯 개 요약 카드를 한 줄 요약 패널로 합쳤다. 성공 여부와 수행

## 11. 작업할 때 지켜야 할 기준

- 원본 rosbag이나 JSON 파일을 화면에서 수정하거나 삭제하지 않는다.
- 실제 관측 위치와 알고리즘이 계산한 목표 위치를 서로 다른 선으로 표시한다.

- 데이터가 없거나 파일이 손상돼도 전체 관제 서버가 종료되지 않게 한다.
- 각 단계를 완료할 때 테스트 결과와 변경 파일을 이 문서에 추가한다.
