# System Monitor 책임 범위와 개발 순서

이 문서가 현재 System Monitor 개발 범위와 순서의 기준이다. 과거 P0 체크리스트는 더 이상 우선순위 기준으로 사용하지 않는다.

## System Monitor가 맡는 것

- Flask 실시간 관제 화면과 공개 상태 API
- ROS/Fleet 메시지를 화면용 공통 상태로 변환
- 두 로봇의 연결, 상태, 배터리, 위치, 방향 표시
- 현재 수신한 탐지·덫 위치와 경고 표시
- ROS 탐지와 map 좌표 이동 경로의 로컬 SQLite 영속 기록·조회
- 확인 후 로컬 탐지·이동 기록과 연결 증거 이미지 전체 초기화
- Offline, 저전압, 대상 유실 상태 표시
- Mock 시나리오와 변환 로직 단위 테스트

## 현재 맡지 않는 것

- 로그인과 사용자 권한 관리
- Incident·Trap·Mission 운영 DB 구현과 소유
- 개별 기록 수정·삭제, 검토 메모와 보고서 생성
- 운영 MySQL 초기화와 데이터 보존 정책
- 로봇 측 탐지 DB 구현 및 소유
- 로봇 내부 자율주행·탐지 알고리즘
- 로봇 이동 명령과 `/fleet/command` 발행

현재 이벤트 목록과 실시간 지도 마커는 서버 실행 중인 메모리 상태다. 별도의
탐지·이동 기록 화면의 일반 조회는 `HistoryStore` SQLite를 읽기 전용으로
처리한다. 전체 초기화만 별도 확인 절차를 거쳐 허용한다.

## 개발 우선순위

1. 실제 `/fleet/status` 수신으로 두 로봇 상태·배터리 검증
2. TF/odom 위치·방향과 `map` 좌표계 일치
3. `/fleet/event`에 필요한 `robot_id`, 사건 종류, 좌표 계약 확정
4. 통신 끊김·재연결·대상 유실·저전압 상태 시험
5. 실제 카메라 스트림 연결 — 구독·캐시·API 배선과 화면의 탐지 오버레이는
   준비·확인 완료(`camera_service.py`), 실물 카메라로 최종 확인만 남음
6. `central_node`가 소유하는 제어 결과를 관제 상태로 정확히 표시

## 공동 확정이 필요한 것

- Topic/Service/Action 이름과 메시지 필드
- 로봇 ID와 좌표 frame 규칙
- Offline 제한 시간과 재연결 처리
- `central_node`가 제공할 제어 상태와 실패 원인 필드
- 로봇 DB가 제공할 조회 인터페이스와 데이터 소유권

로봇 DB가 준비되기 전에는 조회 화면을 가정해 만들지 않는다. 이후 필요성이 확정되면 System Monitor는 DB 파일을 직접 공유하지 않고 서비스/API 계약을 통해 읽는 방식을 우선 검토한다.
