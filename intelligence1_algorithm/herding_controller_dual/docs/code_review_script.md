# 2부 · 왜 이렇게 나눴는가 (모듈 설계)

## 2-1. 가장 중요한 결정 — ROS를 한 파일에 가뒀다

**10개 파일 중 `herding_node.py` 하나만 ROS 라이브러리를 씁니다. 나머지 9개는 ROS가 뭔지도 모릅니다.**

### 이게 무슨 뜻인가

파이썬에서 다른 라이브러리를 쓰려면 파일 맨 위에 `import`를 씁니다.
ROS를 쓰려면 `import rclpy`가 필요합니다.

```python
# herding_node.py — 이 파일에만 있다
import rclpy                    # ← ROS 라이브러리
from rclpy.node import Node

# 나머지 9개 파일 — ROS 관련 import가 아예 없다
import numpy as np              # ← 계산 라이브러리만
```

**즉 나머지 9개 파일은 그냥 "숫자를 넣으면 숫자가 나오는 계산 함수 덩어리"입니다.**
ROS가 설치돼 있든 없든, 로봇이 있든 없든 그냥 돌아갑니다.

```
[ROS 세계]                     [순수 계산 세계]
로봇 위치 토픽  →  herding_node  →  herding_core(x, y, ...) → 목표점
지도 토픽       →  (통역사)      ←  나머지 9개 파일
```

`herding_node.py`는 **통역사**입니다. ROS가 보내주는 메시지를 그냥 숫자로 바꿔서
계산 함수에 넘기고, 계산 결과를 다시 ROS 메시지로 포장해서 내보냅니다.
**통역만 하고 알고리즘은 하나도 안 들어 있습니다.**

### 왜 이렇게 했는가 — 이게 발표의 핵심 중 하나

> "이 구조가 아니었으면 이 프로젝트는 실패했을 겁니다.
>
> 파라미터 하나를 정하려면 **수천 번 돌려봐야** 합니다. 예를 들어 협공 각도를
> 60도로 정할 때, 네 가지 조건을 비교했습니다."

| 비교한 조건 | 시행 |
|---|---|
| 협공 각도 ±60° | 150쌍 |
| 협공 각도 ±90° | 150쌍 |
| 협공 각도 ±120° | 150쌍 |
| 협공 안 씀 (기존 방식) | 150쌍 |

> "**'쌍'이라고 부르는 이유**는 한 번 잴 때마다 같은 상황을 **두 번** 돌리기
> 때문입니다 — 로봇 두 대로 한 번, 로봇 한 대로 한 번. 그래야 '두 번째 로봇 덕분에
> 결과가 바뀌었는지'를 알 수 있습니다.
>
> 그러니까 4가지 조건 × 150쌍 × 2회 = **1,200번**을 돌려서 각도 하나를 정한 겁니다.
> 그리고 이런 스윕을 파라미터마다 했습니다."

**이걸 ROS로 하면 불가능합니다.** ROS 노드를 띄우면 실제 시간으로 돌아가서
한 시행에 30~60초씩 걸립니다. 1,200번이면 **10시간이 넘습니다.** 게다가 로봇이나
시뮬레이터를 계속 켜놔야 합니다.

### 그래서 어떻게 되는가

ROS를 통역사 한 장에 가둬놨기 때문에, 알고리즘을 **그냥 함수처럼 부를 수 있습니다.**

```python
# 검증 스크립트에서 — ROS 없이 이렇게 부른다
core = HerdingCore(config)                 # 알고리즘 준비
output = core.step(observation)            # 한 번 계산 → 목표점 나옴
robot_goal = output.robot1_goal            # 결과 꺼내 쓰기
```

로봇도, ROS도, 실제 시간도 필요 없습니다. **for문으로 수천 번 돌릴 수 있습니다.**
실제로 1,200회 스윕이 몇 분이면 끝나고, 단위 테스트 177개는 **30초**면 끝납니다.

**예상 질문**: "그럼 ROS 부분은 어떻게 테스트하나요?"

> "`herding_node.py` 안에서도 ROS가 없어도 되는 함수(파라미터 매핑, 좌표 변환,
> 확률 격자 만들기)는 순수 함수로 빼서 단위 테스트합니다. 순수하게 ROS 배선인
> 부분만 테스트에서 빠지는데, 그건 리뷰 매뉴얼상 '타 파트 연동'이라 동작 확인만
> 하면 되는 영역입니다."

> "맞습니다. 이 파일 안에 목표점 계산 방식이 여러 개 들어 있습니다 — 기본 몰이,

> 지금은 **왜 그 방식을 안 썼는지가 주석으로 남아 있는 게 더 가치 있다**고 판단해
> 유지했지만, 정리한다면 채택된 것만 남기고 나머지는 별도 파일로 뺄 수 있습니다."

# 3부 · 왜 이 숫자인가 (검증 설계와 임계값)

여기가 **가장 많이 질문받을 부분**이다. "그 숫자 어디서 나왔냐"에 전부 답이 있어야 한다.

## 3-1. 검증 항목과 임계값

```python
ALGO_001_MIN_SUCCESS_RATE  = 0.70    # 성공률 70% 이상
ALGO_002_MAX_MEAN_TIME_SEC = 60.0    # 평균 소요 60초 이하
ALGO_003_MAX_PANIC_RATE    = 0.10    # panic 10% 이하
ALGO_004_MAX_ROLE_SWAPS    = 5       # 역할 전환 5회 이하
ALGO_005_MAX_LATENCY_MS    = 100.0   # 계산 지연 100ms 이하
ALGO_006_MIN_RECOVERY_RATE = 0.80    # 5초 내 재포착 80% 이상
ALGO_008_MIN_DIFFERENCE_PP = 40.0    # 대조군 대비 +40%p 이상
ALGO_008_MAX_P_VALUE       = 0.05    # 유의수준 5%
```

**각 임계값의 근거**

| 항목 | 왜 이 값인가 |
|---|---|
| 성공률 70% | 프로젝트 스펙의 수용 기준. 실제로는 96~98%가 나온다 |
| 평균 60초 | 시연 한 회를 1분 안에 보여줄 수 있어야 한다는 기준 |
| **panic 10%** | 아래 별도 설명 |
| **지연 100ms** | 제어 주기가 10Hz(100ms)라, 계산이 이보다 오래 걸리면 **주기를 못 맞춘다**. 실제 1ms 미만 |
| 재포착 80% | 쥐를 놓쳐도 대부분 다시 찾아야 몰이가 이어진다 |
| **+40%p, p<0.05** | "알고리즘이 없어도 되는 것 아니냐"에 답하는 통제 실험 기준 |

**panic이 뭐고 왜 10%인가**

> "먼저 panic이 뭔지부터 말씀드리겠습니다. 로봇이 쥐에게 너무 가까이 붙으면
> — 정확히는 `panic_distance_m`보다 가까워지면 — 알고리즘이 **로봇을 뒤로
> 물러나게** 합니다. 이걸 panic retreat이라고 부르고, panic률은 **전체 시행 중
> 그 상황이 한 번이라도 일어난 비율**입니다."

**10%라는 숫자의 출처는 정직하게 말씀드리면 프로젝트 스펙의 수용 기준표입니다.**
저희가 실험으로 유도한 값이 아니라, 프로젝트 시작 시점에 정해진 기준을 그대로
가져왔습니다. 코드에도 그렇게 적혀 있습니다.

```python
# --- ALGO-00x 임계값, 스펙의 수용 기준표에서 그대로 가져옴 ---
ALGO_003_MAX_PANIC_RATE = 0.10
```

> "다만 이 지표를 왜 보는지는 설명할 수 있습니다. **panic률이 높다는 건 로봇이
> 쥐에게 계속 위험하게 접근하고 있다는 뜻**입니다. 시뮬레이션에서는 물러나면 그만이지만,
> 실기에서는 **로봇이 RC카를 들이받을 수 있습니다.** 그래서 성공률과 별개로 봐야 하는
> 안전 지표입니다.
>
> 실제로 이 지표 덕분에 걸러낸 게 있습니다. 덫 위치 후보를 고를 때 성공률은
> 86.7%로 나쁘지 않은데 **panic이 43%**인 자리가 있었습니다. 구석이라 로봇이 쥐에
> 바짝 붙어야 했던 겁니다. 성공률만 봤으면 그냥 썼을 텐데, panic률을 보고 탈락시켰습니다."

**지연 100ms는 성능이 아니라 실시간성 기준입니다**

> "제어 주기가 10Hz입니다. 즉 **100ms마다 한 번씩** 계산해서 목표를 내보내야 합니다.
> 계산이 100ms보다 오래 걸리면 주기를 못 맞추고 명령이 밀립니다.
> 실제 측정값은 1ms 미만이라 여유가 큽니다."

## 3-2. 시행 횟수를 100회로 잡은 이유

> "트랩당 100회씩 3곳이니 한 모델당 300회입니다. 이 숫자를 고른 이유가 있습니다.
>
> 개발 중에 **소표본에 두 번 속았습니다.** 60회에서 +5.0%p로 보이던 개선이
> 150쌍으로 늘리니 −4.6%p로 뒤집혔습니다. 그때 배운 게 '표본이 작으면 우연이
> 개선처럼 보인다'는 것이고, 이후로 규칙을 세 개 세웠습니다."

**규칙 1 — 표본을 키운다 (트랩당 100회)**

> "동전을 10번 던져 앞면이 7번 나왔다고 '이 동전은 앞면이 잘 나온다'고 할 수 없습니다.
> 시행이 적으면 우연이 실력처럼 보입니다. 저희가 딱 그렇게 속았습니다."

**규칙 2 — 같은 시드로 짝짓는다**

> "시드는 **난수의 씨앗**입니다. 같은 시드를 주면 컴퓨터가 **완전히 똑같은 난수**를
> 만들어냅니다. 즉 쥐가 어디서 시작하고 어떻게 움직일지가 **완전히 동일하게 재현**됩니다.
>
> 그래서 '로봇 두 대'와 '로봇 한 대'를 비교할 때 **같은 시드를 씁니다.**
> 그러면 두 조건의 차이는 오직 로봇 대수뿐입니다."

```python
# 같은 시드로 두 번 — 조건만 다르게
결과_두대 = 시뮬레이션_실행(시드=1000)          # 로봇 2대
결과_한대 = 시뮬레이션_실행(시드=1000, 한대만)   # 로봇 1대, 쥐 움직임은 완전히 동일
```

> "이걸 안 하면 '두 대 조건에서 우연히 쉬운 상황이 많이 나온 것'과 구분이 안 됩니다."

**규칙 3 — 다른 시드로 재현을 확인한다**

> "시드를 1000번대에서 재고 좋은 결과가 나왔다면, **2000번대·3000번대로 바꿔서
> 다시 재봅니다.** 세 번 다 같은 결론이 나와야 믿습니다.
>
> 한 시드 세트에서만 좋다면, 그건 **그 시드 세트가 우리 알고리즘에 우연히 유리했던 것**일
> 수 있습니다. 실제로 엔드게임 협공은 시드 A/B/C 세 세트에서 모두 재현됐습니다."

## 3-3. 기여도를 재는 방법 — 짝지은 통제 실험

> "'로봇 두 대가 한 대보다 나은 게 당연하지 않냐'는 반문을 막기 위한 설계입니다.
>
> 조건을 완전히 동일하게 두고 **로봇 하나만 제자리에 묶습니다.** 같은 시드를 쓰므로
> 쥐의 초기 위치와 움직임이 완전히 같습니다. 그리고 두 가지를 셉니다."

- **구조(rescue)** — 한 대는 실패했는데 두 대는 성공한 시행
- **역행(regression)** — 그 반대

> "이 둘의 건수 차이를 **이항검정**으로 봅니다. 현재 **구조 14건 : 역행 0건, p = 0.00012**입니다."

### 이항검정이 뭔지 — 동전 던지기로 생각하면 쉽다

> "만약 **두 번째 로봇이 아무 영향도 없다면** 어떻게 될까요?
>
> 두 조건의 결과가 갈린 시행들이 있을 텐데, 그건 그냥 **운**입니다.
> 운이라면 '한 대만 성공'과 '두 대만 성공'이 **반반**으로 나와야 합니다.
> 동전 던지기랑 같습니다.
>
> 그런데 저희 결과는 **14번 던져서 14번 다 같은 면**이 나온 겁니다."

| | 실제 결과 | 운이라면 기대되는 값 |
|---|---|---|
| 구조 (두 대만 성공) | **14** | 약 7 |
| 역행 (한 대만 성공) | **0** | 약 7 |

> "동전을 14번 던져서 전부 앞면이 나올 확률이 얼마일까요?
>
> **1/2를 14번 곱하면 약 0.006%입니다.** 양쪽 방향을 다 고려해도 **0.012%**,
> 이게 p값 0.00012입니다.
>
> 즉 **'두 번째 로봇이 아무 영향 없는데 우연히 이런 결과가 나왔을 확률'이
> 0.012%**라는 뜻입니다. 너무 낮으니 '영향이 없다'는 가정을 버립니다."

### 역행이 0인 게 왜 좋은 건가 — 헷갈리기 쉬운 부분

**"역행이 있어야 비교가 공정해 보이는 것 아닌가?"** 하는 의문이 들 수 있는데, 반대입니다.

| 만약 이랬다면 | 해석 |
|---|---|
| 구조 14 : 역행 **12** | 두 번째 로봇이 결과를 **뒤섞기만** 했다. 어떤 건 살리고 어떤 건 망쳤다 → **효과 없음**. p값도 커서 유의하지 않다 |
| 구조 14 : 역행 **0** | 두 번째 로봇이 **살리기만 하고 망친 적은 없다** → 명백한 개선 |

> "역행이 많으면 '두 대가 낫다'는 주장이 **약해집니다.** 결과가 좋아진 만큼
> 나빠지기도 했다는 뜻이니까요."

### 그럼 "두 대가 나은 건 당연하지 않냐"는 어떻게 막나

이건 **역행 건수가 아니라 다른 두 가지**로 막습니다.

**① 처음엔 당연하지 않았다는 사실**

> "가장 강력한 반박은 **저희 자신의 초기 데이터**입니다.
> 개선 전에는 로봇 두 대를 써도 성공률이 **똑같았습니다** — 450회 중 결과가
> 바뀐 게 1건뿐이었습니다.
>
> **'두 대면 당연히 낫다'가 사실이라면 그때도 나았어야 합니다.** 안 그랬습니다.
> 두 대가 나은 건 당연한 게 아니라, **그렇게 만들어야 되는 것**입니다."

**② 같은 시드로 짝지었다는 설계**

> "'두 대 조건에서 우연히 쉬운 상황이 많이 나온 것 아니냐'는 반문은
> **같은 시드를 쓰기 때문에** 성립하지 않습니다. 쥐의 시작 위치와 움직임이
> 두 조건에서 완전히 동일합니다. 다른 건 로봇 대수뿐입니다."

**정직하게 밝힐 점**

> "이 실험을 설계할 때 실수가 있었습니다. 처음에는 2번 로봇을 무조건 묶었는데,
> 역할이 동적으로 바뀌는 구조라 **13% 시행에서는 미는 역할을 없애버린 것**이었습니다.
> 그래서 구조 15건이 허수로 잡혔습니다. 역할을 보고 묶도록 고치니 구조가 0건이
> 됐습니다 — 그 15건은 알고리즘의 기여가 아니었습니다."

## 3-4. 주요 파라미터의 근거

| 파라미터 | 값 | 근거 |
|---|---|---|
| `drive_distance_m` | 0.30 | **제약**: × 1.15 < `flee_reaction_distance_m`(0.42). 어기면 로봇이 쥐 반응거리 밖에 서서 쥐가 아예 안 도망간다 |
| `flee_reaction_distance_m` | 0.42 | 로봇 한 대 크기(가로 34cm) 기준 가정값 |
| `capture_radius_m` | 0.30 | 0.5m는 방이 좁아 덫끼리·벽과 겹쳤다 |
| `endgame_half_angle_deg` | **60.0** | 실측: 60°=90.0% / 90°=46.0% / 120°=15.3% |
| `endgame_stall_sec` | **3.0** | 실측: 1초=79.3% / 2초=82.7% / 3초=84.0% |
| `robot_radius_m` | 0.175 | 로봇 파트 `nav2.yaml`의 `robot_radius`와 일치시킴 |

> "**모든 파라미터에 근거 주석이 달려 있습니다.** `config/herding_params.yaml`을 열면
> 값 위에 왜 그 값인지, 바꾸면 뭐가 깨지는지가 적혀 있습니다. 특히 `drive_distance_m`은
> 코드가 시작할 때 제약을 검사해서, 위반하면 **노드가 아예 안 뜹니다.**"

# 4부 · 어떤 이론을 어떻게 적용했는가

여기가 발표의 **하이라이트**다. 자세한 내용은 `docs/references.md`.

## 4-1. 출발점 — Shepherding (양치기) 모델

**Strömbom et al. (2014), Journal of the Royal Society Interface**

> "양치기 개가 양떼를 모는 행동을 두 규칙으로 환원한 논문입니다. 핵심 통찰은
> **'밀지 않는다'**는 겁니다. 개는 양을 건드리지 않고, 양이 개로부터 도망치는
> 반응을 이용해 유도합니다.
>
> 저희도 똑같이 합니다. 로봇을 **덫의 반대편**에 세우면, 쥐 자신의 도주 본능이
> 쥐를 덫 쪽으로 밀어냅니다. 코드로는 이 한 줄입니다."

```python
u = target_pos - goal_pos                    # 덫 → 쥐 방향
driving_point = target_pos + drive_distance_m * u   # 쥐 기준 덫 반대편
```

> "**이 한 가지 규칙만으로 로봇 한 대가 92%를 달성했습니다.**"

## 4-2. 그런데 검증해보니 두 번째 로봇이 놀고 있었습니다

**순서가 중요합니다. 이론이 먼저 알려준 게 아니라, 저희가 측정으로 먼저 발견했습니다.**

> "Driving point 방식으로 로봇 두 대를 굴려서 **성공률 92%**가 나왔습니다.
> 숫자만 보면 성공이라 여기서 끝낼 수도 있었습니다.
>
> 그런데 검증을 하나 더 해봤습니다. **두 번째 로봇을 제자리에 묶어놓고 같은 시드로
> 다시 돌린 겁니다.**"

| 조건 | 성공률 |
|---|---|
| 로봇 두 대 | 92% |
| **두 번째 로봇을 묶음** | **92% (동일)** |

> "**성공률이 똑같이 나왔습니다.** 450회 시행 중 두 번째 로봇이 결과를 바꾼 건
> **단 1건(0.2%)**이었습니다.
>
> 즉 92%는 전부 첫 번째 로봇이 만든 숫자였습니다. 게다가 실제 운용에서 첫 번째
> 로봇은 저희 알고리즘이 아니라 detector 파트가 유도합니다. **저희 협동 알고리즘의
> 기여가 0이었다는 뜻입니다.**
>
> 이게 이 프로젝트 최대의 위기였습니다. 기여가 0이면 이 패키지는 존재할 이유가 없습니다."

### 왜 그런지는 나중에 이론이 설명해줬습니다

> "원인을 찾다가 처음 참고했던 논문을 다시 봤습니다. 논문의 규칙은 두 개입니다."

| 규칙 | 내용 | 우리에게 적용되나 |
|---|---|---|
| **Driving** | 목표 반대편에서 밀기 | ✅ 쓰고 있음 |
| **Collecting** | 무리에서 떨어진 개체를 되돌리기 | ❌ **쓸 수가 없음** |

> "**Collecting을 쓸 수가 없습니다.** 논문에서 목동이 여러 마리 필요한 이유가
> 양이 여럿이고 흩어지기 때문인데, 저희 표적은 쥐 **한 마리**입니다.
> 흩어질 무리가 없으니 되돌릴 것도 없습니다.
>
> 즉 **문헌을 그대로 따르면 두 번째 로봇이 할 일이 없습니다.** 저희가 측정으로
> 발견한 '기여 0'이 우연이 아니라 **구조적인 결과**였던 겁니다.
>
> 그래서 문제가 명확해졌습니다 — **문헌에 없는 두 번째 로봇의 역할을 저희가
> 새로 만들어야 했습니다.**"

## 4-3. 이론에서 근거를 찾으려 했고, 틀렸습니다

**Lion and Man (추격-회피 문제)**

> "추격-회피 문헌에 이런 정리가 있습니다 — **같은 속도라면 추격자 1명은 회피자를
> 영원히 못 잡지만, 2명이면 잡을 수 있다.** '두 대가 필요하다'의 수학적 근거로
> 딱 맞아 보였습니다.
>
> 그런데 **두 가지가 틀렸습니다.**"

**틀린 것 ①** — 정리의 전제는 "추격자가 회피자보다 **느리지 않을 것**"인데,
우리 설정은 로봇 0.31 m/s < 쥐 0.40 m/s로 **전제부터 깨져 있었습니다.**

**틀린 것 ②** — 전제를 맞춰(로봇을 더 빠르게) 다시 재도 **두 대의 우위가 안 나왔습니다.**

| 로봇 속도 | 두 대 | 한 대 | p |
|---|---|---|---|
| 0.46 m/s | 74.2% | 75.8% | 0.727 |
| 0.60 m/s | 62.5% | 60.8% | 0.754 |

**왜 정리대로 안 됐는가 — 쉽게 설명하면**

> "정리는 이렇게 말합니다: **'추격자 2명이 잡을 수 있는 방법이 존재한다.'**
>
> 그런데 이건 **'그런 방법이 세상에 있다'**는 뜻이지, **'아무렇게나 두 명이
> 쫓아가면 잡힌다'**는 뜻이 아닙니다.
>
> 비유하자면 이렇습니다. '이 미로에는 출구가 있다'는 건 사실입니다.
> 하지만 그렇다고 **아무 방향으로나 걸으면 나갈 수 있는 건 아닙니다.**
> 출구가 있다는 것과, 내가 그 길을 걷고 있다는 건 다른 얘기입니다.
>
> 정리가 보장하는 '잡는 방법'은 **수학적으로 계산된 최적 전략**입니다.
> 저희 Driver/Blocker 배치는 **휴리스틱**입니다. 최적 전략이 아닙니다."

**휴리스틱(heuristic)이란**: 정답을 수학적으로 계산해서 구하는 대신,
**"이렇게 하면 대체로 잘 되더라"는 경험적 규칙**으로 답을 정하는 방법이다.
빠르고 구현하기 쉽지만, **최선이라는 보장이 없다.**

| | 최적 전략 | 휴리스틱 |
|---|---|---|
| 구하는 법 | 수학적으로 증명 | 경험·직관으로 규칙을 정함 |
| 보장 | 최선임이 보장됨 | **보장 없음** |
| 예 | "이렇게 움직이면 반드시 잡힌다"는 증명된 추격 전략 | "덫 반대편 0.3m에 서면 잘 되더라" |

> "저희 알고리즘은 전부 휴리스틱입니다. Driving point도, 협공 각도 60도도
> **실험해보니 그게 제일 낫더라**는 규칙이지 최적이라는 증명은 없습니다.
>
> **정리는 출구가 있다고 알려줬을 뿐, 저희에게 길을 알려준 게 아니었습니다.**"

**여기서 얻은 교훈 (발표에서 강조할 것)**

> "정리를 인용할 때는 두 가지를 따로 확인해야 합니다.
> **(a) 전제를 실제로 만족하는가, (b) 정리가 보장하는 것이 내가 주장하려는 것과
> 같은가.** 저희는 둘 다 틀렸고, 측정으로 잡았습니다."

## 4-4. 결국 답은 문헌이 아니라 실패 데이터에서 나왔습니다

> "새로운 방법을 또 시도하는 대신, **실패한 시행을 전부 뜯어봤습니다.**"

| 항목 | 값 |
|---|---|
| 실패 92건 중 덫 반경 0.6m 안까지 도달 | **91건** |
| 실패 시행의 덫 최근접 거리 중앙값 | **0.37 m** |
| 포획 반경 | 0.30 m |

> "**몰이는 이미 성공하고 있었습니다.** 실패는 전 구간에 흩어져 있지 않았고,
> 오직 **마지막 7cm**에 몰려 있었습니다.
>
> 왜 그런지도 명확합니다. 미는 로봇 한 대는 쥐의 **뒤**만 막을 뿐 **좌우를 못 막습니다.**
> 넓은 공간에서는 옆으로 새도 다시 몰면 되지만, 덫 바로 앞에서는 한 번 새면
> 그대로 지나쳐 버립니다.
>
> **좌우를 동시에 막으려면 로봇이 두 대 있어야 합니다.** 이것이 두 번째 로봇이
> 구조적으로 필요한 유일한 구간이었습니다."

## 4-5. 그래서 만든 것 — 엔드게임 협공

```
                    발동 반경 0.8m
                  ┌ ─ ─ ─ ─ ─ ─ ─ ┐
                              ● 로봇 A (+60°)
   ★덫  ← ← ← ← ● 쥐
                              ● 로봇 B (−60°)
                  └ ─ ─ ─ ─ ─ ─ ─ ┘
```

**발동 조건 두 가지**

1. 쥐가 덫 반경 **0.8m** 안에 들어오고
2. 그 상태로 **3초간** 포획이 안 되면 (= 평소 방식으로 안 되는 게 확인되면)
3. 두 로봇이 덫 반대편 **±60°**로 갈라져 동시에 압박

**왜 60도인가 — 넓을수록 좋은 게 아니다**

| 각도 | 성공률 |
|---|---|
| **±60° (채택)** | **90.0%** |
| ±90° | 46.0% |
| ±120° | 15.3% |

> "크게 벌리면 **두 로봇 사이가 뚫려** 쥐가 그리로 빠져나가고, 좁히면 두 대가 겹쳐서
> 사실상 한 대가 됩니다. 두 로봇의 몸통이 도주로를 물리적으로 덮는 각도가 존재합니다."

**왜 3초를 기다리는가 — "언제 협동하지 않을지"도 중요하다**

> "즉시 발동하면 아직 정상적으로 몰리고 있는 상황까지 협공으로 바꿔버립니다.
> 그러면 두 로봇이 벌어지느라 미는 힘이 약해져서, 기본 표적 성공률이
> **90.7%에서 72.7%로 떨어집니다.**
>
> 그래서 '먼저 밀어보고, 안 들어가면 그때 협공'으로 조건을 걸었습니다.
> **어떻게 협동할지만큼 언제 협동하지 않을지가 중요했습니다.**"

**이론과 다른 점 — 덫이 세 번째 로봇 역할을 한다**

> "포위(encirclement) 이론에 따르면 2차원에서 표적을 가두려면 **최소 3대**가 필요합니다.
> 2대로는 선분밖에 못 만들고 표적이 돌아서 나갑니다.
>
> 저희는 **덫을 세 번째 꼭짓점으로 씁니다.** 로봇 2대 + 덫 = 삼각형이고,
> 쥐에게 남는 방향이 덫 쪽으로 수렴합니다. 포위가 불가능한 대수로 포위 효과를
> 만든 셈입니다."

# 5부 · 세부 코드

여기서부터 코드를 연다. **line by line은 하지 않고 중요한 곳만.**

## 5-1. 노드 구성 — 하나뿐이다

> "이 패키지가 띄우는 ROS 노드는 `herding_node` 하나입니다."

**용어부터**: ROS에서 노드끼리는 "토픽"으로 데이터를 주고받습니다.

- **구독(subscribe)** = **받는** 데이터. 다른 노드가 보내주는 걸 받아 씁니다.
- **발행(publish)** = **보내는** 데이터. 우리가 만들어서 내보냅니다.

| 방향 | 토픽 | 뜻 | 용도 |
|---|---|---|---|
| **구독** (받음) | `~/target_pose` | 쥐가 지금 어디 있나 | detector 파트가 보내줌 |
| **구독** (받음) | `~/robot1_pose` · `~/robot2_pose` | 두 로봇이 지금 어디 있나 | 로봇 파트가 보내줌 |
| **구독** (받음) | `/map` | 방의 지도 | SLAM이 보내줌 |
| **발행** (보냄) | `~/robot1_goal` · `~/robot2_goal` | **로봇아 여기로 가라** | **최종 산출물** → Nav2로 |
| **발행** (보냄) | `~/herding_state` | 지금 몰이가 어느 단계인가 | 모니터링용 |
| **발행** (보냄) | `~/escape_probability` | 쥐가 어디로 갈 것 같은가 | RViz 시각화용 |

정리하면 **쥐 위치·로봇 위치·지도를 받아서 → 계산해서 → 목표점 2개를 내보냅니다.**

> "중요한 건 **경로 생성과 장애물 회피는 저희가 안 한다**는 겁니다. 저희는
> '어디에 서라'만 알려주고, 거기까지 어떻게 가는지는 Nav2가 합니다."

## 5-2. 핵심 코드 — 협공 지점 계산

```python
def compute_endgame_pincer(target_pos, trap_pos, grid_map, clearance_m,
                           body_clearance_m, stand_distance_m,
                           trigger_radius_m, half_angle_rad=np.pi/3.0):
    # ── 1단계: 지금이 협공할 상황인가? ──────────────────────────────
    to_trap = trap - target                    # 쥐에서 덫으로 향하는 화살표
    dist = float(np.linalg.norm(to_trap))      # 그 화살표의 길이 = 쥐~덫 거리
    if dist > trigger_radius_m or dist < 1e-6:
        return None                            # 쥐가 덫에서 0.8m보다 멀다 → 협공 안 함
                                               # (None = "협공 지점 없음", 평소 몰이 유지)

    # ── 2단계: 어느 방향으로 벌릴지 기준선 잡기 ────────────────────
    inward  =  to_trap / dist                  # 길이를 1로 만든 화살표 (덫 쪽)
    outward = -inward                          # 그 반대 = 덫 반대편 = 로봇이 설 쪽
    perp    = np.array([-outward[1], outward[0]])  # outward를 90도 돌린 방향
                                               # (x,y) → (-y,x)가 90도 회전 공식

    # ── 3단계: 한쪽 로봇이 설 자리 찾기 ────────────────────────────
    def place(sign):                           # sign=+1이면 왼쪽, -1이면 오른쪽
        # 60도로 벌려보고, 벽에 막히면 42도 → 24도로 좁혀 재시도
        for angle in (half_angle_rad, half_angle_rad*0.7, half_angle_rad*0.4):
            # outward에서 angle만큼 돌린 방향 (삼각함수로 원 위의 점을 구함)
            offset = outward*np.cos(angle) + perp*(sign*np.sin(angle))
            point  = target + offset * stand_distance_m   # 쥐에서 그 방향으로 0.3m
            # 그 자리에 로봇 몸통이 들어가나? (벽까지 여유가 충분한가)
            if _cell_clearance(point, grid_map, clearance_m) >= body_clearance_m:
                return point                   # 설 수 있다 → 이 자리로 결정
        return None                            # 세 각도 다 벽에 막힘 → 자리 없음

    # ── 4단계: 양쪽 다 자리가 나와야 협공이 성립 ───────────────────
    point_a, point_b = place(+1.0), place(-1.0)   # 왼쪽·오른쪽 각각 계산
    if point_a is None or point_b is None:
        return None                            # 한쪽이라도 못 서면 협공 포기

    # ── 5단계: 두 로봇이 겹치지 않는지 확인 ────────────────────────
    if float(np.linalg.norm(point_a - point_b)) < 2.0*(body_clearance_m - 0.03):
        return None                            # 두 자리가 너무 가까움 = 로봇끼리 겹침
                                               # 겹친 두 대는 사실상 한 대라 의미 없음

    return PincerPair(point_a=point_a, point_b=point_b, active=True)   # 협공 지점 2개 반환
```

**그림으로 보면**

```
                        point_a  ●  ← place(+1.0), outward에서 +60도
                               ╱
        ★덫 ←── inward ── 쥐 ●━━━→ outward (덫 반대편, 기준선)
                               ╲
                        point_b  ●  ← place(-1.0), outward에서 -60도
```

**설명할 지점 세 곳**

**① 벽에 막히면 각도를 좁혀 재시도합니다**

> "실제 방은 좁아서 60°가 벽에 걸리는 경우가 흔합니다. 그때 포기하는 대신
> 42°, 24°로 좁혀봅니다. 완전한 협공은 아니어도 **없는 것보다는 낫다**는 판단입니다."

**② 두 로봇이 겹치면 `None`을 반환합니다**

> "이건 이론적 방어가 아니라 **실제로 당했던 버그를 막는 코드**입니다.
> 예전에 '압박 페어'라는 방식을 만들었는데 결과가 아주 좋아 보였습니다.
> 알고 보니 시뮬레이터에 로봇 몸통이 없어서 **두 로봇이 겹쳐서 통과**하고
> 있었습니다. 겹친 두 대는 사실상 한 대입니다. 몸통 충돌을 넣고 다시 재니
> 33~45%로 무너졌습니다."

**③ `None`을 반환하면 협공을 포기하고 평소 방식으로 돌아갑니다**

> "협공이 성립 안 하는 상황에서 억지로 하면 오히려 나빠집니다.
> **안 되면 안 하는 것**이 이 함수의 설계 원칙입니다."

## 5-3. 발동 조건 — "3초 동안 계속" 을 어떻게 아는가

**문제**: 알고리즘은 100ms마다 한 번씩 도는데, 매번 "지금 이 순간"만 봅니다.
그런데 우리가 알고 싶은 건 **"3초 동안 계속 덫 근처에 있었나"**입니다.
한 순간만 봐서는 알 수 없습니다.

**해결**: **덫 근처에 처음 들어온 시각을 적어둡니다.** 그리고 매번 "지금 시각 −
적어둔 시각"을 계산하면 얼마나 오래 있었는지 나옵니다.

```python
if distance_to_goal <= self.config.endgame_trigger_radius_m:
    # 쥐가 덫 0.8m 안에 있다
    if self._endgame_entered_sec is None:
        self._endgame_entered_sec = observation.sim_time_sec
        # ↑ 아직 안 적어놨으면 지금 시각을 적는다 (= 스톱워치 시작)
        #   이미 적어놨으면 건드리지 않는다 (스톱워치 계속 감)
else:
    # 쥐가 덫 0.8m 밖으로 나갔다
    self._endgame_entered_sec = None      # 적어둔 걸 지운다 (= 스톱워치 리셋)

stalled = (self._endgame_entered_sec is not None          # 스톱워치가 돌고 있고
           and observation.sim_time_sec - self._endgame_entered_sec
               >= self.config.endgame_stall_sec)          # 3초를 넘겼나
```

**스톱워치라고 생각하면 쉽습니다.**

| 상황 | 하는 일 |
|---|---|
| 쥐가 덫 0.8m 안에 **처음** 들어옴 | 스톱워치 **시작** (시각 기록) |
| 계속 안에 있음 | 아무것도 안 함 (스톱워치 계속 감) |
| 밖으로 **나감** | 스톱워치 **리셋** (기록 지움) |
| 안에서 3초 지남 | **협공 발동** |

> "리셋이 중요합니다. 쥐가 덫 근처를 **잠깐 스쳐 지나간 것**으로는 발동하면 안 됩니다.
> 나갔다 들어오면 다시 0초부터 셉니다. **'3초 동안 계속 갇혀 있었다'**는 게
> 확인돼야 협공으로 전환합니다."

## 5-4. 파라미터 검증 — 잘못된 조합은 시작조차 못 한다

```python
def __post_init__(self):
    if self.drive_distance_m * self.drive_distance_ease_factor \
            >= self.flee_reaction_distance_m:
        raise ValueError(...)
```

> "`drive_distance_m × 1.15`가 `flee_reaction_distance_m`보다 크면, 로봇이 쥐의
> **반응 거리 밖**에 서게 됩니다. 그러면 쥐가 아예 안 도망가서 시스템이 교착됩니다.
>
> 이걸 런타임에 조용히 실패하게 두면 '왜 안 움직이지'로 며칠 헤맵니다. 그래서
> **설정을 읽는 순간 예외를 던져** 노드가 아예 안 뜨게 했습니다."

> **모든 수치는 시뮬레이션 결과입니다. 실물 로봇 검증은 아직 못 했습니다.**
