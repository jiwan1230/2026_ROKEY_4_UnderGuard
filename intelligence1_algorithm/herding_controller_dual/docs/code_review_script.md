**설명 포인트**

> "패키지가 두 개인 이유부터 말씀드리겠습니다. `herding_controller`가 처음 만든 버전이고,

# 2부 · 왜 이렇게 나눴는가 (모듈 설계)

## 2-1. 가장 중요한 결정 — ROS를 한 파일에 가뒀다

**10개 파일 중 `herding_node.py` 하나만 `rclpy`를 import 합니다. 나머지 9개는 ROS를 모릅니다.**

```
herding_node.py     ← rclpy import. ROS 토픽 ↔ 순수 함수 변환만
    ↓ 호출
herding_core.py     ← 순수 파이썬. numpy만 씀
    ↓ 호출
나머지 8개 모듈      ← 순수 파이썬
```

**왜 이렇게 했는가 (이게 발표의 핵심 중 하나)**

> "이 구조가 아니었으면 이 프로젝트는 실패했을 겁니다.
>
> 알고리즘을 튜닝하려면 **수천 번 돌려봐야** 합니다. 각도 하나 정하는 데 150쌍씩
> 4가지 조건을 비교했으니 1,200회입니다. ROS 노드를 띄워서 이걸 하려면 로봇이
> 필요하고, 실시간으로 돌아가니 한 번에 몇 분씩 걸립니다.
>
> ROS 의존성을 어댑터 한 장에 가둬놓으니, 알고리즘을 **그냥 파이썬 함수처럼 호출**할
> 수 있습니다. 시뮬레이터에서 초당 수백 회 돌릴 수 있고, 단위 테스트도 ROS 없이
> 30초면 끝납니다."

**예상 질문**: "그럼 ROS 부분은 어떻게 테스트하나요?"

> "`herding_node.py` 안에서도 ROS가 없어도 되는 함수(파라미터 매핑, 좌표 변환,
> 확률 격자 래스터화)는 순수 함수로 빼서 단위 테스트합니다. 순수하게 ROS 배선인
> 부분만 테스트에서 빠지는데, 그건 리뷰 매뉴얼상 '타 파트 연동'에 해당해서
> 동작 확인만 하면 되는 영역입니다."

## 2-2. 파일을 나눈 기준 — "한 파일 = 한 가지 질문"

| 파일 | 대답하는 질문 | 줄 수 |
|---|---|---|
| `target_estimator.py` | 쥐가 **지금 어디에** 있나? | 100 |
| `escape_model.py` | 쥐가 **어디로 갈까**? | 226 |
| `geodesic_field.py` | 벽을 돌아서 가면 **덫까지 얼마나** 먼가? | 193 |
| `herding_planner.py` | 그래서 **로봇을 어디에** 세울까? | 711 |
| `role_assigner.py` | **누가** 밀고 누가 막을까? | 98 |
| `state_machine.py` | 지금 **어느 단계**인가? | 113 |
| `occlusion_grid.py` | 놓쳤을 때 **어디를 찾을까**? | 61 |
| `grid_map.py` | 미터 ↔ 격자 **좌표 변환** | 72 |
| `herding_core.py` | 위 전부를 **순서대로 엮기** | 849 |
| `herding_node.py` | ROS **입출력 변환** | 395 |

> "각 파일이 한 문장으로 설명되는 질문 하나에 답하도록 나눴습니다.
> 그래야 '쥐가 어디로 갈지 예측이 이상하다' 싶을 때 `escape_model.py`만 보면 됩니다."

**예상 질문**: "`herding_planner.py`가 711줄인데 더 나눌 수 있지 않나요?"

> "맞습니다. 이 파일 안에 목표점 계산 방식이 여러 개 들어 있습니다 — 기본 몰이,
> 차단, 봉인, 압박, 협공. 시도했다가 채택 안 된 것들도 남아 있어서요.
> 지금은 **왜 그 방식을 안 썼는지가 주석으로 남아 있는 게 더 가치 있다**고 판단해
> 유지했지만, 정리한다면 채택된 것만 남기고 나머지는 별도 파일로 뺄 수 있습니다."

## 2-3. 설계도와 코드의 대응

```
입력                 위치 추정        도주 예측        목표점 계산      역할 배정      출력
포즈×3, /map  →  target_estimator → escape_model → herding_planner → role_assigner → 목표점×2
                        └──────── herding_core.step()이 이 순서로 호출 ────────┘
                                    상태 판단: state_machine
```

# 3부 · 왜 이 숫자인가 (검증 설계와 임계값)

여기가 **가장 많이 질문받을 부분**이다. "그 숫자 어디서 나왔냐"에 전부 답이 있어야 한다.

## 3-1. 검증 항목과 임계값

```python
ALGO_001_MIN_SUCCESS_RATE  = 0.70    # 성공률 70% 이상
ALGO_002_MAX_MEAN_TIME_SEC = 60.0    # 평균 소요 60초 이하
ALGO_003_MAX_PANIC_RATE    = 0.10    # panic 10% 이하
ALGO_004_MAX_ROLE_SWAPS    = 5       # 역할 전환 5회 이하
ALGO_005_MAX_LATENCY_MS    = 100.0   # 계산 지연 100ms 이하
ALGO_006_MIN_RECOVERY_RATE = 0.80    # 5초 내 재포착 80% 이상
ALGO_008_MIN_DIFFERENCE_PP = 40.0    # 대조군 대비 +40%p 이상
ALGO_008_MAX_P_VALUE       = 0.05    # 유의수준 5%
```

**각 임계값의 근거**

| 항목 | 왜 이 값인가 |
|---|---|
| 성공률 70% | 프로젝트 스펙의 수용 기준. 실제로는 96~98%가 나온다 |
| 평균 60초 | 시연 한 회를 1분 안에 보여줄 수 있어야 한다는 기준 |
| **panic 10%** | panic = 로봇이 쥐에 너무 가까워져 물러나는 상황. 자주 일어나면 **로봇이 쥐를 들이받을 위험**이 있다는 신호라 안전 기준이다 |
| **지연 100ms** | 제어 주기가 10Hz(100ms)라, 계산이 이보다 오래 걸리면 **주기를 못 맞춘다**. 실제 1ms 미만 |
| 재포착 80% | 쥐를 놓쳐도 대부분 다시 찾아야 몰이가 이어진다 |
| **+40%p, p<0.05** | "알고리즘이 없어도 되는 것 아니냐"에 답하는 통제 실험 기준 |

**설명 포인트 — panic과 지연이 안전·실시간성 기준이다**

> "성공률만 보면 안 됩니다. panic률은 **로봇이 쥐에 얼마나 위험하게 접근하는지**를
> 재는 안전 지표고, 지연은 **제어 주기를 지킬 수 있는지**를 재는 실시간성 지표입니다.
> 실제로 덫 위치를 고를 때 성공률이 높은데 panic이 43%인 후보가 있었고, 그건
> 탈락시켰습니다."

## 3-2. 시행 횟수를 100회로 잡은 이유

> "트랩당 100회씩 3곳이니 한 모델당 300회입니다. 이 숫자를 고른 이유가 있습니다.
>
> 개발 중에 **소표본에 두 번 속았습니다.** 60회에서 +5.0%p로 보이던 개선이
> 150쌍으로 늘리니 −4.6%p로 뒤집혔습니다. 그때 배운 게 '표본이 작으면 우연이
> 개선처럼 보인다'는 것이고, 이후로 규칙을 세 개 세웠습니다."

1. **표본을 키운다** — 트랩당 100회
2. **같은 시드로 짝짓는다** — 두 조건에 완전히 동일한 난수를 쓴다
3. **다른 시드로 재현을 확인한다** — 시드 세트를 바꿔 결과가 유지되는지 본다

## 3-3. 기여도를 재는 방법 — 짝지은 통제 실험

> "'로봇 두 대가 한 대보다 나은 게 당연하지 않냐'는 반문을 막기 위한 설계입니다.
>
> 조건을 완전히 동일하게 두고 **로봇 하나만 제자리에 묶습니다.** 같은 시드를 쓰므로
> 쥐의 초기 위치와 움직임이 완전히 같습니다. 그리고 두 가지를 셉니다."

- **구조(rescue)** — 한 대는 실패했는데 두 대는 성공한 시행
- **역행(regression)** — 그 반대

> "이 둘의 건수 차이를 이항검정으로 봅니다. 현재 **구조 14건 : 역행 0건, p = 0.00012**입니다."

**예상 질문**: "왜 성공률 차이만 보지 않고 구조/역행을 세나요?"

> "성공률 차이는 '평균적으로 몇 % 낫다'만 말해줍니다. 구조/역행은 **같은 상황에서
> 결과가 뒤집힌 횟수**라 인과에 훨씬 가깝습니다. 그리고 역행이 0건이라는 건
> '두 번째 로봇이 방해가 된 적은 없다'는 뜻이라 따로 볼 가치가 있습니다."

**정직하게 밝힐 점**

> "이 실험을 설계할 때 실수가 있었습니다. 처음에는 2번 로봇을 무조건 묶었는데,
> 역할이 동적으로 바뀌는 구조라 **13% 시행에서는 미는 역할을 없애버린 것**이었습니다.
> 그래서 구조 15건이 허수로 잡혔습니다. 역할을 보고 묶도록 고치니 구조가 0건이
> 됐습니다 — 그 15건은 알고리즘의 기여가 아니었습니다."

## 3-4. 주요 파라미터의 근거

| 파라미터 | 값 | 근거 |
|---|---|---|
| `drive_distance_m` | 0.30 | **제약**: × 1.15 < `flee_reaction_distance_m`(0.42). 어기면 로봇이 쥐 반응거리 밖에 서서 쥐가 아예 안 도망간다 |
| `flee_reaction_distance_m` | 0.42 | 로봇 한 대 크기(가로 34cm) 기준 가정값 |
| `capture_radius_m` | 0.30 | 0.5m는 방이 좁아 덫끼리·벽과 겹쳤다 |
| `endgame_half_angle_deg` | **60.0** | 실측: 60°=90.0% / 90°=46.0% / 120°=15.3% |
| `endgame_stall_sec` | **3.0** | 실측: 1초=79.3% / 2초=82.7% / 3초=84.0% |
| `robot_radius_m` | 0.175 | 로봇 파트 `nav2.yaml`의 `robot_radius`와 일치시킴 |

> "**모든 파라미터에 근거 주석이 달려 있습니다.** `config/herding_params.yaml`을 열면
> 값 위에 왜 그 값인지, 바꾸면 뭐가 깨지는지가 적혀 있습니다. 특히 `drive_distance_m`은
> 코드가 시작할 때 제약을 검사해서, 위반하면 **노드가 아예 안 뜹니다.**"

# 4부 · 어떤 이론을 어떻게 적용했는가

여기가 발표의 **하이라이트**다. 자세한 내용은 `docs/references.md`.

## 4-1. 출발점 — Shepherding (양치기) 모델

**Strömbom et al. (2014), Journal of the Royal Society Interface**

> "양치기 개가 양떼를 모는 행동을 두 규칙으로 환원한 논문입니다. 핵심 통찰은
> **'밀지 않는다'**는 겁니다. 개는 양을 건드리지 않고, 양이 개로부터 도망치는
> 반응을 이용해 유도합니다.
>
> 저희도 똑같이 합니다. 로봇을 **덫의 반대편**에 세우면, 쥐 자신의 도주 본능이
> 쥐를 덫 쪽으로 밀어냅니다. 코드로는 이 한 줄입니다."

```python
u = target_pos - goal_pos                    # 덫 → 쥐 방향
driving_point = target_pos + drive_distance_m * u   # 쥐 기준 덫 반대편
```

> "**이 한 가지 규칙만으로 로봇 한 대가 92%를 달성했습니다.**"

## 4-2. 그런데 여기서 문제가 생겼습니다

> "논문에는 규칙이 두 개입니다. 하나는 방금 말한 **Driving**(뒤에서 밀기)이고,
> 다른 하나는 **Collecting**(무리에서 떨어진 개체를 되돌리기)입니다.
>
> 그런데 **저희는 Collecting을 쓸 수가 없습니다.** 논문에서 목동이 여러 마리 필요한
> 이유가 양이 여럿이고 흩어지기 때문인데, 저희 표적은 쥐 한 마리입니다.
> 흩어질 무리가 없으니 Collecting이 할 일이 없습니다.
>
> 즉 **문헌상 두 번째 로봇의 자리가 없었습니다.** 이게 이 프로젝트 최대의 난관이었고,
> 실제로 검증해보니 로봇 B의 기여가 0으로 나왔습니다."

## 4-3. 이론에서 근거를 찾으려 했고, 틀렸습니다

**Lion and Man (추격-회피 문제)**

> "추격-회피 문헌에 이런 정리가 있습니다 — **같은 속도라면 추격자 1명은 회피자를
> 영원히 못 잡지만, 2명이면 잡을 수 있다.** '두 대가 필요하다'의 수학적 근거로
> 딱 맞아 보였습니다.
>
> 그런데 **두 가지를 틀렸습니다.**"

**틀린 것 ①** — 정리의 전제는 "추격자가 회피자보다 **느리지 않을 것**"인데,
우리 설정은 로봇 0.31 m/s < 쥐 0.40 m/s로 **전제부터 깨져 있었습니다.**

**틀린 것 ②** — 전제를 맞춰(로봇을 더 빠르게) 다시 재도 **두 대의 우위가 안 나왔습니다.**

| 로봇 속도 | 두 대 | 한 대 | p |
|---|---|---|---|
| 0.46 m/s | 74.2% | 75.8% | 0.727 |
| 0.60 m/s | 62.5% | 60.8% | 0.754 |

> "이유는 명확합니다. 정리가 말하는 '2명이면 잡는다'는 **최적 전략을 쓸 때**의
> 이야기입니다. 저희 배치는 휴리스틱이지 그 최적 전략이 아닙니다.
> **정리는 그런 전략이 존재한다는 걸 보장할 뿐, 저희 알고리즘이 그 전략이라는
> 뜻이 아니었습니다.**"

**여기서 얻은 교훈 (발표에서 강조할 것)**

> "정리를 인용할 때는 두 가지를 따로 확인해야 합니다.
> **(a) 전제를 실제로 만족하는가, (b) 정리가 보장하는 것이 내가 주장하려는 것과
> 같은가.** 저희는 둘 다 틀렸고, 측정으로 잡았습니다."

## 4-4. 결국 답은 문헌이 아니라 실패 데이터에서 나왔습니다

> "새로운 방법을 또 시도하는 대신, **실패한 시행을 전부 뜯어봤습니다.**"

| 항목 | 값 |
|---|---|
| 실패 92건 중 덫 반경 0.6m 안까지 도달 | **91건** |
| 실패 시행의 덫 최근접 거리 중앙값 | **0.37 m** |
| 포획 반경 | 0.30 m |

> "**몰이는 이미 성공하고 있었습니다.** 실패는 전 구간에 흩어져 있지 않았고,
> 오직 **마지막 7cm**에 몰려 있었습니다.
>
> 왜 그런지도 명확합니다. 미는 로봇 한 대는 쥐의 **뒤**만 막을 뿐 **좌우를 못 막습니다.**
> 넓은 공간에서는 옆으로 새도 다시 몰면 되지만, 덫 바로 앞에서는 한 번 새면
> 그대로 지나쳐 버립니다.
>
> **좌우를 동시에 막으려면 로봇이 두 대 있어야 합니다.** 이것이 두 번째 로봇이
> 구조적으로 필요한 유일한 구간이었습니다."

## 4-5. 그래서 만든 것 — 엔드게임 협공

```
                    발동 반경 0.8m
                  ┌ ─ ─ ─ ─ ─ ─ ─ ┐
                              ● 로봇 A (+60°)
   ★덫  ← ← ← ← ● 쥐
                              ● 로봇 B (−60°)
                  └ ─ ─ ─ ─ ─ ─ ─ ┘
```

**발동 조건 두 가지**

1. 쥐가 덫 반경 **0.8m** 안에 들어오고
2. 그 상태로 **3초간** 포획이 안 되면 (= 평소 방식으로 안 되는 게 확인되면)
3. 두 로봇이 덫 반대편 **±60°**로 갈라져 동시에 압박

**왜 60도인가 — 넓을수록 좋은 게 아니다**

| 각도 | 성공률 |
|---|---|
| **±60° (채택)** | **90.0%** |
| ±90° | 46.0% |
| ±120° | 15.3% |

> "크게 벌리면 **두 로봇 사이가 뚫려** 쥐가 그리로 빠져나가고, 좁히면 두 대가 겹쳐서
> 사실상 한 대가 됩니다. 두 로봇의 몸통이 도주로를 물리적으로 덮는 각도가 존재합니다."

**왜 3초를 기다리는가 — "언제 협동하지 않을지"도 중요하다**

> "즉시 발동하면 아직 정상적으로 몰리고 있는 상황까지 협공으로 바꿔버립니다.
> 그러면 두 로봇이 벌어지느라 미는 힘이 약해져서, 기본 표적 성공률이
> **90.7%에서 72.7%로 떨어집니다.**
>
> 그래서 '먼저 밀어보고, 안 들어가면 그때 협공'으로 조건을 걸었습니다.
> **어떻게 협동할지만큼 언제 협동하지 않을지가 중요했습니다.**"

**이론과 다른 점 — 덫이 세 번째 로봇 역할을 한다**

> "포위(encirclement) 이론에 따르면 2차원에서 표적을 가두려면 **최소 3대**가 필요합니다.
> 2대로는 선분밖에 못 만들고 표적이 돌아서 나갑니다.
>
> 저희는 **덫을 세 번째 꼭짓점으로 씁니다.** 로봇 2대 + 덫 = 삼각형이고,
> 쥐에게 남는 방향이 덫 쪽으로 수렴합니다. 포위가 불가능한 대수로 포위 효과를
> 만든 셈입니다."

## 5-2. 핵심 코드 — 협공 지점 계산

```python
def compute_endgame_pincer(target_pos, trap_pos, grid_map, clearance_m,
                           body_clearance_m, stand_distance_m,
                           trigger_radius_m, half_angle_rad=np.pi/3.0):
    to_trap = trap - target
    dist = float(np.linalg.norm(to_trap))
    if dist > trigger_radius_m or dist < 1e-6:
        return None                      # 멀면 개입 안 함 — 평소 몰이 유지

    inward  =  to_trap / dist
    outward = -inward                    # 덫 반대편 = 미는 쪽
    perp    = np.array([-outward[1], outward[0]])

    def place(sign):
        # 벽에 막히면 각도를 좁혀 재시도 (60° → 42° → 24°)
        for angle in (half_angle_rad, half_angle_rad*0.7, half_angle_rad*0.4):
            offset = outward*np.cos(angle) + perp*(sign*np.sin(angle))
            point  = target + offset * stand_distance_m
            if _cell_clearance(point, grid_map, clearance_m) >= body_clearance_m:
                return point
        return None

    point_a, point_b = place(+1.0), place(-1.0)
    if point_a is None or point_b is None:
        return None
    # 두 로봇이 겹치면 협공이 성립하지 않는다 → 포기하고 평소 방식 유지
    if float(np.linalg.norm(point_a - point_b)) < 2.0*(body_clearance_m - 0.03):
        return None
    return PincerPair(point_a=point_a, point_b=point_b, active=True)
```

**설명할 지점 세 곳**

**① 벽에 막히면 각도를 좁혀 재시도합니다**

> "실제 방은 좁아서 60°가 벽에 걸리는 경우가 흔합니다. 그때 포기하는 대신
> 42°, 24°로 좁혀봅니다. 완전한 협공은 아니어도 **없는 것보다는 낫다**는 판단입니다."

**② 두 로봇이 겹치면 `None`을 반환합니다**

> "이건 이론적 방어가 아니라 **실제로 당했던 버그를 막는 코드**입니다.
> 예전에 '압박 페어'라는 방식을 만들었는데 결과가 아주 좋아 보였습니다.
> 알고 보니 시뮬레이터에 로봇 몸통이 없어서 **두 로봇이 겹쳐서 통과**하고
> 있었습니다. 겹친 두 대는 사실상 한 대입니다. 몸통 충돌을 넣고 다시 재니
> 33~45%로 무너졌습니다."

**③ `None`을 반환하면 협공을 포기하고 평소 방식으로 돌아갑니다**

> "협공이 성립 안 하는 상황에서 억지로 하면 오히려 나빠집니다.
> **안 되면 안 하는 것**이 이 함수의 설계 원칙입니다."
