# 개발 과정 8단계 타임라인 — 강사 피드백 대응 자료

이 프로젝트가 "왜 엔드게임 협공을 만들게 됐는지"를 시간순으로 정리한 것.
숫자·인용문은 `herding_controller_트러블슈팅_노트.md`(1,874줄)와
`docs/code_review_script.md`, git 커밋 로그에서 그대로 가져왔다. GIF는
`tests/media/`에 있다.

**중요**: 아래 GIF 중 1·2·4·5단계와 3단계-봉인선분은 지금 코드로 새로
돌려서 뽑은 것이라, 그 순간의 실제 알고리즘 동작이다. 3단계-게이트만
**재구성판**이다 (원본 코드가 커밋된 적이 없어 좌표를 그대로 되살릴 수
없음 — 아래 3단계 항목에 별도 표시).

## 1단계 — Driver–Blocker 구조로 92% 달성

교과서적인 접근: 로봇 1(Driver)이 쥐 뒤에 서서 밀고, 로봇 2(Blocker)가
예측된 도주로를 지킨다. 숫자만 보면 성공.

**GIF**: [`tests/media/stage1_driver_blocker_baseline.gif`](tests/media/stage1_driver_blocker_baseline.gif)
— 지금 코드(플랜A, `herding_controller`)로 새로 뽑음. 플랜A는 협공 기능이
아예 없어서, 지금 그대로 돌리는 것 자체가 "1단계의 구조"다. (92%라는 수치는
재-SLAM 이전 맵에서 잰 것이므로 이 GIF로 그 수치를 재현하는 게 아니라
구조 자체를 보여주는 용도.)

## 2단계·위기 — 기여도 검증에서 로봇 B의 기여 = 0

`experiments/blocker_contribution_ablation.py`로 같은 시드에 대해 "막는
로봇이 정상 작동"과 "막는 로봇을 스폰 위치에 완전히 고정"을 짝지어
돌렸더니, 450 시행 중 결과가 바뀐 건 **1건(0.2%)**뿐이었다
(노트 13-3, 16-1).

**GIF**: [`tests/media/stage2_robot_b_zero_contribution.gif`](tests/media/stage2_robot_b_zero_contribution.gif)
— 같은 시드로 두 조건을 나란히 돌린 것. 왼쪽(정상)과 오른쪽(고정) 결과가
소요시간까지 완전히 같다(seed=7000000, 14.0s=14.0s). 재확인 중 발견한
사례도 참고: seed 7000025/7000026은 로봇 B를 얼리면 오히려 실패로
바뀌었고(regression), seed 7000039는 반대로 로봇 B가 있어야 성공했다
(rescue) — "기여가 아예 없다"가 아니라 "살리는 만큼 죽여서 평균이 0"이라는
이야기(16-13)와 정확히 같은 패턴이다.

## 3단계 — 16가지 개선 시도, 전부 실패

로봇 B의 기여를 만들어보려고 시도한 것 전부 (트러블슈팅 노트 11~16번
섹션 누적). "16가지"는 정확히 16개짜리 표가 아니라, 시도가 쌓이면서
노트 안에서 13번(16-8) → 15번(16-11) → 그 이후 추가 2건까지 늘어난
것이다.

| # | 시도 | 결과 |
|---|---|---|
| 1 | `blocking_point_commit_sec` 스윕 | 효과 없음 |
| 2 | 회피 모델 4종(DecisiveFlee/JukingFlee 등) | 효과 없음 또는 악화 |
| 3 | `block_lookahead_m` 양방향 재스윕 | 효과 없음 |
| 4 | `compute_blocking_point` geodesic 재설계 | 효과 없음 |
| 5 | "B가 준비될 때까지 A 대기" | 효과 없음, 소요시간만 27~40% 증가 |
| 6 | 교착(deadlock) 감지·해제 | 26건 중 2건만 수정 |
| 7 | escape_model 반발항 게이팅 | 해는 없앴지만 기여는 없음 |
| 8 | 동적 역할 배정(플랜B) | 이득은 최초 배정(부트스트랩)뿐, 협력 아님 |
| 9 | **봉인 선분**(물리적 차단) | 이 방에서 기하학적으로 불가능 — 봉인 가능 비율 **0.2%** |
| 10 | 압박 선분(좌우 협착) | 로봇-로봇 겹침 버그 제거 후 재측정하니 **33~45%로 대폭 악화** |
| 11 | **장애물(게이트) 설치** | 봉인 가능 비율은 0.4%→13%로 올랐지만 성공률 **92%→15.8%로 붕괴** |
| 12 | 도주 분포 직접 최적화(shaping) | 86.7%로 악화 |
| 13 | 수비-쓸기(Guard & Sweep, lion-and-man 전략) | 기본 표적에서 77.5% vs 89.2% — 유의하게 나쁨(p=0.003) |
| 14 | 구석회피 모델 재검증 (60시행→150쌍) | 60시행 +5.0%p로 유망해 보였으나, 표본을 3배로 늘리자 **-4.6%p로 뒤집힘** |
| — | (해결) 엔드게임 협공 | 39.3%→84.0%, 구조 67:역행 0 → 6단계 |

**GIF (봉인 선분, #9)**: [`tests/media/stage3_sealing_line_impossible.gif`](tests/media/stage3_sealing_line_impossible.gif)
— `compute_sealing_pair()`는 실제로는 어디에도 연결된 적 없는 코드라
시뮬레이션으로 못 보여준다(원래 측정도 기하학적 계산이었다, 16-2). 그래서
실제 표적 이동 경로 위에서 매 순간 "로봇이 순간이동해서 선다면 막을 수
있는가"를 계산해 보여준다 — 이 시행 192프레임 내내 단 한 번도
봉인되지 않았다(0.0%), 노트의 0.2%와 같은 이야기.

**GIF (게이트, #11) — [재구성판, 원본 좌표 없음]**:
[`tests/media/stage3_gate_reconstruction.gif`](tests/media/stage3_gate_reconstruction.gif)
— 원본 게이트 실험은 즉석 스크립트로 돌리고 커밋을 안 해서, 정확한 칸막이
좌표가 남아있지 않다. 같은 실패 메커니즘(트랩으로 가는 길목 자체를
막아버림)을 재구성: bottom 트랩 앞에 칸막이를 놓고 트랩과 어긋난 위치에만
0.8m 틈을 냈다. 재구성판 결과: 게이트 없음 19/20(95%) → 게이트 있음
**0/20(0%)**. 원본 수치(92%→15.8%)와 정확히 같지는 않지만(재구성이라 더
극단적으로 나옴), "봉인 가능성만 최적화하면 몰이 자체가 무너진다"는
결론은 동일하다.

측정 규칙 교훈(#14, CLAUDE.md에도 반영됨): **작은 표본에서 나온 개선은
반드시 짝지은 시드로 표본을 키워 재확인한다.** 60시행 +5.0%p가 150쌍에서
-4.6%p로 뒤집힌 게 바로 이 사례다.

## 4단계·진단 — 표적 모델이 너무 단순했음을 확인

주 검증 모델 `ReactiveFlee`를 다시 읽어보니, 반응거리 밖에서는 그냥
가만히 서 있는 물체였다(노트 16-9). 실제 쥐처럼 "궁지에 몰리면 위협의
옆을 스쳐 빠져나가는" 모델(`CorneringAwareFlee`)을 도입하자 알고리즘이
붕괴했다.

**GIF**: [`tests/media/stage4_realistic_target_collapse.gif`](tests/media/stage4_realistic_target_collapse.gif)
— [재구성] 협공 기능을 끈 상태(엔드게임 협공 도입 이전과 동일 조건) +
구석회피 표적(intensity=3.0)으로 60회 실행, 실패 20건(33%) 중 대표
시행 하나. 원본 수치(39.3%, 트러블슈팅 노트 16-15)와 맵·설정이 달라
정확히 같지는 않지만 같은 붕괴 현상을 보여준다.

## 5단계·전환점 — 실패 전수분석: 실패의 대부분이 마지막 7cm

구석회피 표적의 실패 92건 중 **91건이 트랩 0.6m 안까지 왔다**(트랩
최근접 거리 중앙값 0.37m, 포획 반경 0.30m) — 몰이는 이미 성공하고 있었고,
문제는 마지막 구간뿐이라는 게 여기서 밝혀졌다.

**GIF**: [`tests/media/stage5_last_7cm_failure.gif`](tests/media/stage5_last_7cm_failure.gif)
— 4단계와 같은 조건의 실패 시행 중, 트랩에 제일 가까이(0.40m) 갔다가
결국 옆으로 빠져나간 시행의 마지막 30초.

## 6단계·해결 — 엔드게임 협공 구현

표적이 트랩 0.8m 안에서 3초 넘게 안 잡히면, 두 로봇이 트랩 반대편
좌우 ±60도로 갈라져 도주로를 막는다. 39.3%→84.0%, 구조 67 : 역행 0,
p<0.00001 (3개 독립 시드로 재현, 좌표 갱신 이전 맵 기준).

**GIF**: [`tests/media/endgame_pincer_demo_1.gif`](tests/media/endgame_pincer_demo_1.gif),
[`tests/media/endgame_pincer_demo_2.gif`](tests/media/endgame_pincer_demo_2.gif) — 이미 확보됨.

## 7단계 — 물리 보정

로봇 몸통 반경, 로봇끼리 충돌, 덫의 물리적 포획(닿으면 실제로 멈춤)을
시뮬레이터에 반영하고 재검증했다(노트 섹션 15, 커밋 `d46c9de`/`8388362`/`5059ef7`).

## 8단계 — 재-SLAM 좌표 이전

로봇 파트가 방을 다시 SLAM해서 지도 원점이 이동, 덫·로봇 스폰 좌표를
전부 `(+0.61, +2.95)`로 변환하고 재검증(커밋 `2cf04da`, `8ca4a4d`).
현재 성공률 96.0%/98.0%, 로봇 B 기여 14:0(p=0.00012)으로 유지. 이번
자료에는 별도 GIF 없음 — 위 1~6단계 GIF가 전부 이 새 지도 기준이다.
