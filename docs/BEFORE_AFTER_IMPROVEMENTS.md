# System Monitor 개선 전·후 기록

- 작성일: 2026-08-05
- 대상: `rokey_4_mini_sysmon_starter`
- 실행 모드: Mock

## 1. 비교 기준

이 문서에서 **개선 전**은 개별 ROS 노드의 로그와 토픽을 직접 확인하던 상태를 의미한다.
**개선 후**는 현재 구현된 Flask 기반 System Monitor 스타터를 의미한다.

현재 저장소에는 이전 버전의 Git 이력이 없으므로, 아래 내용은 `README.md`, `docs/`, 현재 소스 코드와 실제 Mock 실행 화면을 기준으로 정리했다.

## 2. 전체 개선 요약

| 구분 | 개선 전 | 개선 후(현재) | 개선 효과 |
|---|---|---|---|

| 임무 현황 | 개별 노드 동작으로 추정 | 임무 상태와 진행률을 KPI로 표시 | 임무 진행 상황의 가시성 향상 |

| 이벤트 | 터미널 로그에 분산 | 시간, 로봇, 심각도를 포함한 이벤트 타임라인 제공 | 이상 상황과 명령 이력 추적이 쉬워짐 |
| 데이터 보존 | 실행 중 메시지 위주 | SQLite3에 탐지 및 시스템 이벤트 저장 | 재실행 후에도 탐지 기록 검색 가능 |

| 사용자 접근 | 별도 웹 인증 없음 | 로그인, 세션, 로그아웃 제공 | 비인가 사용자의 화면 접근 제한 |
| 상태 표현 | ROS 로그와 노드별 표현에 의존 | `IDLE`, `TRACKING`, `TARGET_LOST` 등 공통 상태 정의 | 서로 다른 입력을 동일한 기준으로 표시 |
| 로봇 없는 시험 | 실제 장비 또는 별도 입력 필요 | 자동 Mock 시나리오와 수동 테스트 이벤트 제공 | 장비 없이 UI와 데이터 흐름 시연 가능 |
| 실행 모드 | 실제 ROS 환경 중심 | `MONITOR_MODE=mock/ros`로 실행 방식 분리 | 개발·시연과 실제 연동 환경을 구분 가능 |
| 화면 대응 | 관제 화면 없음 | 데스크톱 3열 화면과 기본 반응형 레이아웃 제공 | PC와 모바일에서 기본적인 화면 접근 가능 |

## 3. 디자인 개선 내용

### 개선 전

- 로그와 숫자 중심이라 중요한 상태의 우선순위를 한눈에 구분하기 어려웠다.
- 로봇, 지도, 탐지, 이벤트 사이의 관계를 운영자가 직접 연결해서 판단해야 했다.
- 정상, 경고, 연결 끊김을 공통된 시각 언어로 표현하는 화면이 없었다.

### 개선 후

- 어두운 관제 화면에 민트, 주황, 빨강을 사용해 로봇과 탐지·경고를 구분했다.
- 상단 KPI에 온라인 로봇, 임무 진행률, 탐지 기록, 활성 경고를 배치했다.
- 로봇 상태 → 지도 → 카메라 → 이벤트 순서로 정보를 구성했다.
- 선택된 로봇 카드를 테두리로 강조하고, 온라인·오프라인 상태를 색상으로 표시했다.
- Mock/ROS 모드와 서버 수신 상태를 화면 상단에서 확인할 수 있게 했다.
- 탐지 DB를 관제 화면과 분리해 실시간 관제와 사후 검토의 목적을 구분했다.

## 4. 기능 개선 내용

### 관제 기능

- 두 로봇의 역할과 상태를 동시에 조회한다.
- 1초 주기로 최신 상태를 가져와 화면을 갱신한다.
- 로봇별 임무 시작, 일시정지, 복귀, 임무 중단 명령을 제공한다.
- 최근 탐지 좌표와 로봇 진행 방향을 지도에 표시한다.
- 배터리 부족, 대상 유실, 덫 설치 완료 등의 이벤트를 시험할 수 있다.

### 데이터 기능

- 탐지 결과를 SQLite3에 저장한다.
- 로봇 ID, 객체 종류, 검토 상태로 탐지 기록을 검색한다.
- 탐지 결과를 `REVIEWED` 상태로 변경할 수 있다.
- 시스템 이벤트도 DB에 기록해 이후 감사 로그 확장의 기반을 마련했다.

### 구조 및 연동

- ROS 또는 Mock 입력을 `StateManager`의 단일 상태 모델로 집계한다.
- 로봇 데이터가 제한 시간 동안 수신되지 않으면 `OFFLINE`으로 처리한다.
- 기존 `webcam/detections`, `oakd/detections` 인터페이스를 ROS Bridge에서 받을 수 있게 구성했다.
- 실제 제어 인터페이스가 확정되기 전에는 ROS 모드 명령을 안전하게 거절하도록 설계했다.

검증 결과 1920×1080에서 페이지, 로봇 목록, 카메라, 최근 이벤트 영역의 `scrollHeight`와 `clientHeight`가 모두 같았고, 최근 이벤트는 4개, 로봇 상세 카드는 1개만 렌더링됐다. 전체 이벤트 모달에서만 `overflow: auto`가 활성화되는 것을 확인했다.

| KPI 카드가 약 117px 높이 | 필수 4개 지표를 44px 상태 스트립으로 변경 | 지표는 유지하면서 세로 공간 절약 |
| KPI 숫자와 라벨이 세로로 쌓이고 진행률 막대가 높이 계산을 늘림 | 라벨·숫자를 가로 배치하고 진행률 막대를 카드 하단 2px로 축소 | 카드 겹침 제거와 정보 밀도 향상 |
| 관제 그리드 최소 높이 660px를 강제 | `화면 높이 - 174px`를 관제 영역 높이로 사용하고 최소 높이를 520px로 축소 | 900px 전후 화면에서 하단 잘림 방지 |
| 화면 높이와 관계없이 카메라 영상 높이가 유사 | 영상 높이를 화면 높이의 18% 범위에서 자동 조절 | 카메라와 상태 정보가 패널 안에 유지 |
| 상단 영역 이후 남은 공간 계산이 부정확 | 로봇·지도·카메라 영역이 `y=174`부터 화면 하단까지 사용 | 중요 관제 정보를 화면 중앙에 최대화 |

최신 검증에서 1635×900은 관제 그리드가 `174~900px`, 1366×768은 `174~768px` 범위에 정확히 배치됐다. 두 해상도 모두 페이지 높이와 뷰포트 높이가 같았고 브라우저 오류는 발생하지 않았다.

### 지도 선과 탐지 객체 구분 개선

| 개선 전 | 개선 후(반영 완료) | 개선 효과 |
|---|---|---|
| 세로 점선, 대상 연결선, 이동 경로의 설명이 없음 | 지도 범례에 현재 대상 연결, 최근 이동 경로, 통로 기준선을 명시 | 선의 의미를 화면 안에서 즉시 확인 |
| 대상 연결선과 통로 기준선의 점선 형태가 유사 | 대상 연결은 굵은 원형 점선, 통로는 옅고 긴 점선으로 분리 | 서로 다른 공간 정보의 혼동 방지 |
| 쥐·쥐구멍·배설물이 모두 빨간 원 | 쥐는 빨간 원, 쥐구멍은 보라색 마름모, 배설물은 황금색 삼각형 사용 | 색상과 형태 두 기준으로 객체 식별 |
| 현재 대상 연결선 끝에 객체 종류 표시 없음 | 연결선 끝에도 해당 객체 도형 표시 | 로봇이 어떤 대상을 보고 있는지 명확화 |
| 최근 탐지 라벨이 같은 색상 | 객체 종류에 맞춘 라벨 색상 적용 | 라벨과 마커 관계 강화 |
| 범례가 항상 없거나 의미가 축약됨 | 지도 내부 상시 범례와 범례 표시 토글 제공 | 초보 사용자 안내와 화면 공간 선택권 제공 |
| 센서와 Mock의 객체 이름이 다름 | `LIVE_RODENT`, `ENTRY_POINT`, `DROPPINGS`로 저장 전 정규화 | 모드 간 데이터 계약 통일 |

선의 최종 의미는 다음과 같다.

- 로봇 색상의 굵은 원형 점선: 로봇과 현재 인식 대상의 연결
- 민트색 또는 주황색 곡선 실선: 로봇의 최근 이동 경로
- 옅은 세로 긴 점선: Mock 창고 통로 기준선

검증 결과 지도 범례 8개 항목이 표시되고, 범례 버튼으로 표시·숨김이 동작했으며, 지도 하단 잘림과 브라우저 오류는 발생하지 않았다.

### 현재 대상과 과거 탐지 중복 표시 해결

| 개선 전 | 개선 후(반영 완료) | 개선 효과 |
|---|---|---|
| 저장된 과거 탐지와 현재 대상을 항상 동시에 표시 | 기본 화면에는 활동 중인 로봇의 현재 대상만 표시 | 실시간 관제에 불필요한 마커 제거 |
| `탐지 지점` 토글의 제어 범위가 불명확 | 버튼을 `과거 탐지`로 변경하고 기본 비활성화 | 토글 역할을 명확하게 표현 |
| 현재 대상과 과거 기록의 스타일이 유사 | 현재 대상에 외곽 링과 `현재 객체명` 라벨 추가 | 현재 상태와 기록을 즉시 구분 |
| 과거 탐지를 최대 20개 표시 | 과거 모드에서도 최근 5개만 표시 | 지도 혼잡도 제한 |
| 가까운 동일 객체가 개별 마커로 반복 표시 | 같은 객체가 0.15m 이내이면 하나로 병합하고 `×횟수` 표시 | 반복 탐지의 시각적 중복 제거 |
| 현재 대상과 같은 위치의 과거 기록도 중복 표시 | 같은 객체가 현재 대상 0.15m 이내이면 과거 마커 제외 | 현재·과거 마커 겹침 방지 |
| 완료·대기 상태에서도 마지막 대상이 현재 대상처럼 표시 | 추적·탐색 등 활동 상태에서만 현재 대상 표시 | 오래된 대상의 현재 상태 오인 방지 |
| Mock에서 다른 객체 이벤트가 기존 대상 좌표를 재사용 | 객체 종류가 다르면 객체별 독립 오프셋 좌표 생성 | 쥐구멍·배설물 등 다른 객체의 인위적 겹침 방지 |

검증 시 저장된 탐지 6개와 활동 중인 현재 대상 2개가 존재했지만 기본 화면에는 현재 대상 2개만 표시됐다. `과거 탐지` 활성화 시에만 제한된 기록이 추가됐고, 0.07m 간격의 동일 객체 두 건이 한 클러스터 `×2`로 병합되는 것을 확인했다. Mock 좌표 분리 테스트 2개를 추가해 전체 10개 테스트가 통과했다.

### 로봇 2대 카메라 동시 관제

| 개선 전 | 개선 후(반영 완료) | 개선 효과 |
|---|---|---|
| 선택한 로봇 1대의 카메라만 표시 | robot4와 robot5 카메라를 오른쪽 열에 위아래로 동시 표시 | 로봇을 전환하지 않고 두 작업 상황을 비교 |
| 카메라 전환을 별도 드롭다운으로 수행 | 카메라 카드 자체를 클릭하거나 키보드로 선택 | 조작 단계를 줄이고 선택 대상을 직관적으로 변경 |
| 카메라 선택과 다른 관제 영역의 연결이 약함 | 카메라 선택 시 로봇 탭·상태 카드·지도 강조가 함께 변경 | 현재 제어 대상의 일관성 확보 |
| 최근 이벤트 패널이 오른쪽 열의 약 40%를 차지 | 데스크톱 이벤트 패널을 상단 `이벤트 N` 버튼과 전체 이력 모달로 이동 | 두 번째 카메라를 위한 공간 확보 |
| 카메라마다 구분 정보가 부족 | CAM 번호, 로봇명, 역할, 연결 상태, 수신 경과시간을 헤더에 표시 | 어느 로봇 영상인지 즉시 식별 |
| 영상 상태와 대상 정보가 화면 아래 별도 카드 | 모드·영상·거리·소스를 영상 하단의 반투명 정보 막대로 통합 | 카메라별 정보를 좁은 영역에서도 함께 확인 |
| 각 카메라에 전체화면 버튼이 있어 좁은 헤더와 영상 위에 조작 요소가 추가됨 | CAM1·CAM2 전체화면 버튼과 관련 동작 제거 | 실제 관제에 불필요한 조작을 줄이고 영상 영역 단순화 |
| 화면 크기가 바뀌어도 단일 카메라 중심 배치 | 데스크톱은 세로 2분할, 중간 화면은 가로 2분할, 모바일 카메라 탭은 세로 2개 배치 | 해상도별 비교성과 가독성 유지 |

브라우저 검증 결과 1635×900에서 robot4와 robot5 카메라가 각각 358px 높이로 오른쪽 열에 모두 표시됐으며 페이지 세로·가로 스크롤이 발생하지 않았다. 1366×768에서는 각각 292px 높이를 확보했다. 카메라 선택 동기화와 이벤트 모달은 유지되고 전체화면 버튼은 0개이며, 브라우저 오류 없음과 백엔드 테스트 13개 통과를 확인했다.

### 최초 쥐 탐지 기반 역할 자동 배정

| 개선 전 | 개선 후(반영 완료) | 개선 효과 |
|---|---|---|
| robot4는 추적, robot5는 탐색·트랩 역할로 시작부터 고정 | 두 로봇 모두 `SCOUT` 공동 탐색 역할로 시작 | 로봇 번호가 아닌 실제 탐지 결과로 역할 결정 |
| 역할을 `ROBOT_ROLES=RAT_TRACKER,SURVEY_TRAP` 순서로 지정 | 기본 설정을 `ROBOT_ROLES=SCOUT,SCOUT`으로 변경 | 배포 설정과 협업 시나리오 일치 |
| robot4만 Mock 쥐 탐지를 담당 | Mock 최초 탐지 로봇을 두 로봇 중 선택하고 수동 테스트 탐지도 동일 규칙 적용 | robot5가 먼저 발견하는 반대 상황도 시연 가능 |
| 탐지 후에도 기존 역할 유지 | 최초 탐지 로봇은 `RAT_TRACKER`, 나머지는 `SURVEY_TRAP`으로 원자적 자동 배정 | 거의 동시 탐지에서도 역할 충돌 방지 |
| 후속 쥐 탐지에 대한 역할 유지 규칙 없음 | 한 임무에서 최초 배정 이후 역할 변경을 차단 | 추적 중 역할이 갑자기 뒤바뀌는 문제 방지 |
| 역할 변경 과정이 운영자에게 보이지 않음 | `ROLE_ASSIGNED` 이벤트에 최초 발견 로봇과 각 역할을 기록 | 자동 판단 근거와 결과 확인 가능 |
| 역할과 맞지 않는 시작 명령도 상태 모델에서 허용 | 공동 탐색·쥐 추적·쥐구멍 탐색 시작 명령을 역할별 검증 | 잘못된 역할 명령 차단 |
| 화면에 고정 역할만 표시 | 로봇 탭·상태 카드·카메라 헤더가 현재 동적 역할을 실시간 표시 | 모든 관제 영역에서 역할 일관성 확보 |

검증에서는 robot5가 먼저 쥐를 탐지하도록 실행해 robot5가 `RAT_TRACKER/TRACKING`, robot4가 `SURVEY_TRAP/SEARCHING`으로 자동 변경되는 것을 확인했다. 이후 robot4에서 쥐 탐지를 추가해도 역할은 유지됐다. 역할·명령 테스트 3개를 추가해 전체 13개 테스트가 통과했으며, 1635×900 웹 화면에서 로봇 카드와 두 카메라의 역할 문구가 일치하고 브라우저 오류나 화면 세로 넘침이 없음을 확인했다.

| 우선순위 | 현재 상태 | 향후 개선 방향 |
|---|---|---|
| P1 | 두 카메라 관제 UI는 완성됐지만 영상은 실제 영상이 아닌 자리 표시 화면 | robot4·robot5 ROS compressed image 또는 스트리밍 서버 연동 |
| P1 | 최초 탐지 기반 역할은 상태·화면에 자동 반영되지만 실제 로봇 행동 명령 전송은 미연동 | 역할 배정 결과를 각 로봇의 ROS Action/Service로 전달하고 수락·실행 결과 확인 |
| P1 | 명령 요청은 표시하지만 실제 ROS 결과·피드백 연동 전 | Action feedback과 result를 명령 상태에 연결 |
| P2 | 실제 PGM/YAML 크기 자동 맞춤은 구현 | 사용자 확대·축소와 실시간 OccupancyGrid 갱신 제공 |
| P2 | 활성 경고를 로봇 현재 상태에서 바로 계산 | 경고별 ID와 확인·해결 이력을 갖는 생명주기 모델 추가 |
| P2 | 탐지 조회가 최대 200개이며 브라우저에서 페이지를 분할 | 서버 페이지네이션과 CSV 내보내기 추가 |

## 8. 실제 ROS 운영 전 필수 보완

- 초기 관리자 비밀번호와 기본 `SECRET_KEY`를 변경한다.
- 로그인 화면의 기본 비밀번호 자동 입력을 제거한다.
- CSRF 보호와 역할별 명령 권한을 추가한다.
- ROS 및 DB에서 전달되는 문자열을 안전하게 출력하도록 처리한다.
- 명령 요청, 수락, 실행 중, 성공, 실패를 서로 다른 상태로 기록한다.
- 마지막 상태 수신 시각과 통신 지연시간을 표시한다.
- 비상정지, 복귀 등 안전 관련 명령의 정책을 로봇 담당자와 확정한다.

## 9. 결론

현재 버전은 분산된 ROS 상태와 탐지 정보를 하나의 웹 관제 화면으로 통합하고, 실제 로봇 없이도 전체 흐름을 확인할 수 있게 개선되었다. 특히 시각적 상태 확인, 탐지 기록 보존, Mock 시나리오 측면에서 시연용 스타터의 목적을 충족한다.

이번 웹 개선으로 **명령 상태 유지, 실행 결과 피드백, 현재 경고 계산, 모바일 탐색,
실제 PGM/YAML 지도와 탐지·트랩 위치 표시, 실제 탐지 검토 절차**가 보강되었다.
다음 단계는 실제 카메라·실시간 OccupancyGrid·ROS Action 결과를 연결하고 운영 보안을
강화하는 것이다.
